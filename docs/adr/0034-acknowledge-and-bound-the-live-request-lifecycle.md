# Acknowledge and Bound the Live Request Lifecycle

After protocol validation, peer authorization, Ingress Budget reservation, one-time Model Alias resolution, and basic Revision checks, an Unavailable direct or Alias-selected Revision receives a Domain Rejection before Request Acceptance, consumes no connection-local request sequence, creates no Request ID, and never causes automatic Alias repointing. Otherwise Request Acceptance creates a Request ID from Daemon Instance ID, Connection ID, and a strictly contiguous connection-local sequence allocated only on successful acceptance. It acknowledges the frozen Revision, Request Status Version one, and initial Preparing state; this is not Admission. Preparing obtains the stateless Request Description and complete finite Capability Requirement Set under its own timeout, while a non-resident Revision enters Warming. Immediately before Admission, both paths revalidate the frozen Revision, derive the complete exact-key closure under fresh environment evidence, verify Certification Applicability for every Key, and check Timing Profile, Resource Mode, Owner-Thread Support interference, and capacity without resolving the Alias again. Rejection terminally fails the accepted request with a Structured Error and Tombstone, creates no Resource Reservation or Backend ownership, makes no release call, and is not retried transparently. Only successful Admission atomically freezes the Authorized Capability Set, Resource Reservation, and Timing Commitment, after which Request Materialization creates private Backend state before Queued. Cancellation or failure before materialization starts makes no Backend release call and withdraws any complete unconsumed Resource Reservation; once complete or partial ownership exists, terminal status retains the Request Backend Allocation Budget until accepted Request State Release consumes it, while daemon-owned Reservation components settle under their own rules.

One Data Plane connection may own multiple bounded requests, may query or cancel only its own, and disconnect orders cancellation for all; no later connection can take ownership, query an old Tombstone, or resume output. Privileged inspection and management cancellation belong to the audited Control Plane. Cancellation Accepted is the Direct Response emitted after the Runtime Core commits the cancellation event at its Event Sequence; it confirms authorization and ordering, not terminal state or interruption of an in-flight Turn. A status query returns the current Request Status Snapshot. A Status Subscription first sends that snapshot and then later versions, never historical replay. Queued non-terminal updates wholly superseded by a newer snapshot may coalesce with an explicit History Gap; terminal updates never silently disappear, and lack of their reserved capacity disconnects the client. The snapshot exposes Request ID, frozen Revision, status version, lifecycle state, phase, input and generated-token progress, last Output Sequence, cancellation state, and terminal reason, but no Model Ledger, internal queue position, or Backend handle. Every terminal transition produces an independent terminal Status Update.

The connection uses one bidirectional typed-frame socket with separately bounded Direct Response, one rejection, ordinary Output, and terminal-Status capacity. A command reserves its maximum Direct Response before Event Loop admission and retains that charge through complete frame write or connection termination; enqueue converts reservation to occupancy. The socket writer places that full response before every Status or Output the command causes, without client acknowledgement, while unrelated commands may complete out of Command ID order. The plane-specific Hello freezes and returns no-progress and maximum-completion write durations within binary hard maxima. Once the oldest required frame is eligible at the writer head, those monotonic values bound its write without mid-connection change; either expiry becomes Client Disconnect, releases every outbound reservation, and orders cancellation of all owned non-terminal requests without dropping or retransmitting that frame. Each committed Turn produces at most one bounded Output Frame per request with contiguous token IDs, starting Output Sequence, status version, and optional terminal reason, ordered by stable Turn Plan membership and Effect dependencies. Successful enqueue after the Core commit is Output Publication. If one transition produces final tokens and a terminal state, the Output Frame is published before the terminal Status Update. Frames are live and at most once with no acknowledgement or replay; a later socket-write failure causes Client Disconnect and cancellation without retransmission. Terminal status becomes a count- and time-bounded Tombstone containing no content. A connection-local Request High-Water Mark retains bounded knowledge after eviction: an authorized absent ID at or below it returns Gone, another connection's ID is forbidden, and a foreign-instance or not-yet-issued ID is unknown. Command Exhausted is announced by `command_ingress_closed` on the final Direct Response, stops later command reads, and preserves existing-request Status, Output, and disconnect cancellation.

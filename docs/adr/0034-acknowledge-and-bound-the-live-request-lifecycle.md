# Acknowledge and Bound the Live Request Lifecycle

After protocol validation, peer authorization, Ingress Budget reservation, one-time Model Alias resolution, and basic Revision checks, an Unavailable direct or Alias-selected Revision receives a Domain Rejection before Request Acceptance, consumes no connection-local request sequence, creates no Request ID, and never causes automatic Alias repointing. Otherwise Request Acceptance creates a Request ID from Daemon Instance ID, Connection ID, and a strictly contiguous connection-local sequence allocated only on successful acceptance. It acknowledges the frozen Revision, Request Status Version one, and initial Preparing state; this is not Admission. Preparing obtains the stateless Request Description and complete finite Capability Requirement Set under its own timeout, while a non-resident Revision enters Warming. Immediately before Admission, both paths revalidate the frozen Revision, derive the complete exact-key closure under fresh environment evidence, verify Certification Applicability for every Key, and check Timing Profile, Resource Mode, both Core ledger generations, the exact Runtime Overhead Bound Set's support and sequenced-event interference, fixed capacity for actual initial-Materialization, initial-Candidate-Formation and release Support Operation Obligations plus a reusable Future Turn Support Entitlement with a complete Support Outstanding Credit Vector covering separate Receipt-observation and conditional-continuation-formation obligations versus rejection/local-stale formation and terminal cancellation-membership-change formation, and all non-support resource capacity without resolving the Alias again. Rejection terminally fails the accepted request with a Structured Error and Tombstone, creates no Resource Reservation or Backend ownership, makes no release call, and is not retried transparently. Only successful Admission atomically coordinates both ledgers and freezes the Authorized Capability Set, exact Bound Set, composite Resource Reservation, Timing Commitment, all initial obligations, reusable Future Turn Support Entitlement/vector, and finite per-Turn and terminal membership-change operation requirements, after which Request Materialization creates private Backend state before Queued; its accepted success only completes the initial-formation obligation's predecessor, and first Candidate Formation begins later from already conserved capacity after the materialization envelope ends. Cancellation or failure before materialization starts makes no Backend release call and atomically withdraws every unconsumed component from its owning ledger; once complete ownership exists, terminal status retains the Request Backend Allocation Budget until accepted Request State Release consumes it. A partial-ownership Materialization failure is already terminal: Core closes the now-impossible initial-Candidate-Formation obligation and Future Turn Support Entitlement, retains the distinct release obligation and complete Backend Allocation Budget until that same accepted release, and settles other daemon-owned Reservation components under their own rules.

The entitlement vector additionally reserves request-specific capacity for terminal cancellation-membership-change Candidate Formation. Queued cancellation invalidates any candidate and not-started Plan containing the request, then atomically rebinds, splits, merges, or closes their unstarted operation obligations and creates one shared terminal formation obligation for surviving members only when required; only a later standalone `begin_support` transition after the cancellation envelope ends may start Candidate Formation. Pre-materialization cancellation withdraws every Resource Capacity Ledger component and all unconsumed initial/release obligations and entitlement claims. Post-materialization cancellation before first formation closes the initial-formation obligation and entitlement, withdraws daemon output/transient capacity, and retains only Backend ownership, Budget, and release obligation. Queued cancellation or Critical Eviction follows the same daemon-component withdrawal after membership invalidation. In-flight cancellation retains daemon output/transient capacity until the synchronized Receipt and its directly resulting enqueue/discard have transferred or released concrete occupancy and no operation remains in flight; Backend Budget settlement remains exclusively result-gated.

One Data Plane connection may own multiple bounded requests, may query or cancel only its own, and disconnect orders cancellation for all; no later connection can take ownership, query an old Tombstone, or resume output. Privileged inspection and management cancellation belong to the audited Control Plane. Cancellation Accepted is the Direct Response emitted after the Runtime Core commits the cancellation event at its Event Sequence; it confirms authorization and ordering, not terminal state or interruption of an in-flight Turn. A status query returns the current Request Status Snapshot. A Status Subscription first sends that snapshot and then later versions, never historical replay. Queued non-terminal updates wholly superseded by a newer snapshot may coalesce with an explicit History Gap; terminal updates never silently disappear, and lack of their reserved capacity disconnects the client. The snapshot exposes Request ID, frozen Revision, status version, lifecycle state, phase, input and generated-token progress, last Output Sequence, cancellation state, and terminal reason, but no Model Ledger, internal queue position, or Backend handle. Every terminal transition produces an independent terminal Status Update.

The connection uses one bidirectional typed-frame socket with separately bounded Direct Response, one rejection, ordinary Output, and terminal-Status capacity. A command reserves its maximum Direct Response before Event Loop admission and retains that charge through complete frame write or connection termination; enqueue converts reservation to occupancy. The socket writer places that full response before every Status or Output the command causes, without client acknowledgement, while unrelated commands may complete out of Command ID order. The plane-specific Hello freezes and returns no-progress and maximum-completion write durations within binary hard maxima. Once the oldest required frame is eligible at the writer head, those monotonic values bound its write without mid-connection change; either expiry becomes Client Disconnect, releases every outbound reservation, and orders cancellation of all owned non-terminal requests without dropping or retransmitting that frame. Each committed Turn produces at most one bounded Output Frame per request with contiguous token IDs, starting Output Sequence, status version, and optional terminal reason, ordered by stable Turn Plan membership and Effect dependencies. Successful enqueue after the Core commit is Output Publication. If one transition produces final tokens and a terminal state, the Output Frame is published before the terminal Status Update. Frames are live and at most once with no acknowledgement or replay; a later socket-write failure causes Client Disconnect and cancellation without retransmission. Terminal status becomes a count- and time-bounded Tombstone containing no content. A connection-local Request High-Water Mark retains bounded knowledge after eviction: an authorized absent ID at or below it returns Gone, another connection's ID is forbidden, and a foreign-instance or not-yet-issued ID is unknown. Command Exhausted is announced by `command_ingress_closed` on the final Direct Response, stops later command reads, and preserves existing-request Status, Output, and disconnect cancellation.

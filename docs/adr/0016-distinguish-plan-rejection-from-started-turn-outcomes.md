# Distinguish Plan Rejection from Started Turn Outcomes

Immediately before `execute_turn`, the Event Loop checks the Turn Plan's complete Generation Vector and exact Runtime Overhead Bound Set identity against current Core state. On mismatch it makes no Backend call and submits one Local Stale Plan Core Event carrying the mismatch witness, currently active qualified intrinsic Stale Plan Disposition Bound, the Plan's frozen intrinsic successor ceiling, and its still-valid shared rejection/local-stale Candidate-Formation obligation. The dedicated Core transition validates that current bound independently of the stale Set, closes the Plan exactly once, emits the audited Domain Rejection plus intrinsic fresh-scheduling Effects, and rejects duplicate, unknown, or Backend-result-shaped input. The local bound ends before any `form_candidates` preparation; the local transition only marks that operation obligation pending or closes it on typed causal impossibility. After that intrinsic envelope ends, a standalone Core `begin_support` transition converts the pending obligation immediately before the Event Loop measures one separate Candidate Formation support envelope. Before any resulting fresh Snapshot, the Event Loop uses the same synchronized scheduling-trigger cut, bounded prefix, and mandatory-crossing allowance as every other scheduling path. The local-stale path consumes no Engine Service and produces neither Plan Rejection nor Turn Receipt; unavailable, excessive, over-ceiling, or missing operation-obligation evidence fail-stops without fabricating an event outcome. For a still-current Plan, a Backend-owned Candidate, state, or bound validation may return a Plan Rejection before MLX execution starts; that complete direct-call interval is Runtime Overhead, consumes zero Engine Service, produces no Turn Receipt, and likewise reaches a fresh Snapshot only through that common cut under the same intrinsic/support split. Once Backend execution begins, exactly one synchronized Turn Receipt is required while the Executor remains alive. Batch Receipts contain per-request Member Outcomes, but recovery is per member only when the Backend proves persistent-state isolation; otherwise the entire Batch is quarantined. Output remains staged until the Scheduler accepts the Receipt and atomically commits request state, after which explicitly ordered Effects enqueue at most one Output Frame per member into capacity reserved before execution; successful enqueue is Output Publication. Strictly contiguous Event Sequence resolves cancellation races: cancellation command acceptance confirms only that ordering; if ordered first it enters Cancel Pending and discards staged output at the safe boundary, while a cancellation ordered after Receipt commit and Output Publication cannot revoke visible output. An independent Status Update reports the actual terminal state even when a final Output Frame also carries a terminal reason. Duplicate or late Effect Results are rejected and never publish or commit a second time.

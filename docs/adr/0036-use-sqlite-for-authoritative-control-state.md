# Use SQLite for Authoritative Control State

The single-writer SQLite Control Store and serialized durable Control Mutation apply to every Serving Profile. Identity Anchor publication, Runtime Metadata, Bundle, Restore, Clone, multi-authority repair, Compatibility Custody, and Bounded Integrity Lifecycle mechanisms in this decision apply only to the Integrity Serving Profile.

The P0 Serving Profile uses one SQLite database, one bounded executor, one connection, and one current-generation pointer as its complete durable Control authority. Its versioned schema owns the immutable Runtime Identity Record with its exact Storage Qualification Record binding, complete Control State Generations, current pointer, P0 Audit Sequence State, and at most one exact Pending Audit Envelope. The sequence state is a sibling authority outside the semantic Control State Snapshot, not an Audit Journal copy. `ATTACH`, a second database, Runtime Metadata tables, Authority Publication Staging, an Audit continuation pointer, and any other current-selector path are forbidden in P0.

Every successful P0 write transaction uses `journal_mode=DELETE`, `synchronous=FULL`, `fullfsync=ON`, and `temp_store=MEMORY`, followed by explicit synchronization of the database parent directory. Commit and parent synchronization are separate crash boundaries but one Native Authority barrier: no range becomes assignable, generation becomes active, pending envelope becomes cleared, or operation succeeds between them. Control Initialization creates P0 Audit Sequence State; afterward only range reservation updates it through this barrier before assignment and never reduces or reuses a possibly published value. Control Mutation consumes an already-reserved sequence and leaves the state unchanged.

Range reservation is the sole daemon-owned pre-operation Store primitive: it consumes no Event Sequence and creates no Core Event, Effect, Result, mutation Operation ID, Audit Record, or Pending Audit Envelope. Exact absence leaves the old high-water, exact commit-plus-parent success publishes the new one, and an indeterminate commit or parent barrier latches Storage Barrier Failure without a mutation ID or Control Outcome Indeterminate response. No same-session retry or unchanged-high-water claim is allowed; Bootstrap classifies exact sequence-state bytes before later assignment.

P0 Control Initialization, while already holding the Daemon Instance Lock, acquires the installation qualification lock and verifies that the exact Storage Qualification Record named by Installation Policy is Head-selected and matches the Runtime Authority Volume, OS build, TurnVector build, and Profile. The offline qualifier never acquires a Runtime lock. Initialization holds the qualification lock through the database-parent synchronization that publishes the immutable binding, then may release it. It publishes that binding with the daemon-generated Runtime ID and History Epoch ID, complete version-one state with explicitly empty scoped registries, initial sequence range, sole current pointer, and exact pending Epoch Open envelope in one guarded `FULL` transaction. After rollback recovery, absent bytes remain Uninitialized; one exact committed candidate retains its qualification, IDs, generation, range, and envelope and receives a repeated parent synchronization; any third state is non-ready. The daemon never creates a second identity because a commit may have occurred. The exact Epoch Open is then appended, synchronized, verified, and cleared through another guarded commit-plus-parent barrier before initialization succeeds; an actually attempted required-barrier failure returns `initialization_outcome_indeterminate` without a Control Mutation Operation ID or Token.

For every later P0 Control Mutation, Store helpers may encode rows only inside a caller-owned transaction. Bounded validation first proves the full build-derived Control Mutation Sequence Headroom remains inside already durable ordinary ranges, completing range reservation when necessary before a Control Mutation Operation ID exists and without borrowing Terminal Sequence Reserve. At a synchronized boundary the Runtime Event Loop revalidates the complete mutation token, current next value, and headroom; drift returns a no-ID state conflict. Only then does the daemon allocate one Operation ID and Core atomically record the prepublication Effect, one-in-flight proposal owner, and headroom charge before the Audit Writer begins bounded Predecessor Fence attempts. Every permitted ordinary assignment decrements that charge. Individual stale attempts create no Core Event; exhaustion consumes the current next value for one sequenced nonpublication failure Effect Result and closes the operation/headroom and reopens the Runtime Closure Gate before typed busy, while Audit Degraded retains the exact Operation Ledger stage and charge. At a synchronized Turn boundary the Event Loop revalidates a granted fence and complete token, enters the Control Publication Commit Barrier by assigning the protected Store-result slot to the pending Store publication Effect Result, and submits the complete successor, pointer, and exact Pending Audit Envelope while leaving sequence state unchanged. Only that pre-sequenced transition may run until the bounded executor returns. Parent synchronization completes publication, and its trustworthy committed Result drives C19 activation, owner advance, and one dependent exact-envelope completion Effect while retaining the final protected Result slot before barrier release. Exact Audit append and verification followed by a guarded pending-clear transaction and parent synchronization return that Effect's ordinary sequenced Result; only its accepted Core transition acknowledges success and releases owner/headroom. An ordinary append failure keeps the same Effect and charge pending for supervised recovery. No helper, retry path, Bootstrap classifier, or Audit record can advance the current pointer independently.

A trustworthy exact-absent Store outcome consumes the pre-sequenced Store-result slot as one nonpublication failure Result, preserves the predecessor, and closes the Effect/owner/headroom without activation or a dependent Effect; an indeterminate outcome produces no Result. After committed C19 success, barrier release permits only headroom-charged bounded safety, Runtime Closure Registry-approved nonincreasing transitions, and exact-envelope completion; the Runtime Closure Gate remains closed and discretionary Turn dispatch stays deferred until the completion Result releases the owner. Audit Safety Reserve prevents ordinary saturation from blocking those bounded records.

Mutation-owner creation atomically closes the Core-owned Runtime Closure Gate until the terminal Result. Its exhaustive build-generated registry rejects or defers every Core transition that increases future sequence-and-Audit closure liability, including Request Acceptance, Core connection-state creation, Reservation or Residency Demand creation, and new independent Operations or Effects. Fence interleaving may only advance or replace already charged closure obligations without increasing their registered remaining maximum; read-only status with no Core object remains available.

Commit Barrier entry closes the exact Event Loop-owned `{Daemon Instance ID, Operation ID, checked nonzero barrier generation}` Control Mutation Cancel Gate after the Store-result sequence and barrier stage exist and before external I/O; its session-local generation advances on every publication and never wraps. Following authorization, protocol and Command ID validation, cancellation-ingress and Direct Response reservation, and ordered enqueue, the Event Loop rechecks the gate before Core conversion and completes that admission decision before a later command advances. While any gate is closed, an exact tuple returns `cancel_window_closed` and a different or unknown Daemon Instance ID, Operation ID, or barrier generation returns opaque `commit_in_progress` without disclosing identity existence. Both are daemon protocol-stage Direct Responses with no Core Event, Event Sequence, Effect Result, Audit Record, Domain Rejection, headroom charge, Store-outcome claim, unchanged-state claim, or retained command; complete write or connection termination releases the reservation. The gate persists through C19 and Storage Barrier Failure and clears only with terminal owner release. Disconnect of the originating Control Plane connection ends only mutation-result delivery and contributes at most one deduplicated transition; Data Plane Client Disconnect still cancels every owned request through already budgeted transitions. Neither overtakes classification, rolls back the committed candidate, repeats Store publication, or releases the owner.

P0 Bootstrap creates the global Storage Barrier Failure guard, freezes and validates the Installation Policy-selected exact Storage Qualification Record against the actual volume, OS build, TurnVector build, and Profile, and only then opens this database for rollback recovery. For initialized or exactly committed identity bytes, it requires the immutable Runtime Identity Record to bind that same record before any later Runtime write; mismatch is Storage Capability Missing, not implicit rebind. After rollback recovery it classifies each durable boundary by its own evidence and never recovers a session-local Predecessor Fence or in-memory Control Mutation Sequence Headroom. Initialization is absent, one exact committed candidate whose pending Epoch Open uses the Epoch Genesis Hash, or invalid. Range reservation is absent, one exact committed P0 Audit Sequence State with no Pending Audit Envelope, or invalid. Control Mutation is absent, one exact committed candidate carrying an exact persisted predecessor hash and record identity, or invalid; Bootstrap may append only when the current verified Audit head equals that predecessor, or clear only after the exact record is already verified in-chain. Pending-clear is classified separately as uncleared, exactly cleared, or invalid. Every exact candidate receives only its missing parent barrier, and every exact Pending Audit Envelope completes before Audit tail handling; none is derived from a state diff. After a Control Mutation Operation ID exists, only an actually attempted required Fence file/parent synchronization, SQLite commit, database-parent synchronization, post-append Audit file/parent synchronization or verification, or pending-clear commit/parent synchronization failure returns Control Outcome Indeterminate without a fabricated Result, latches one session outcome, stops Device work, and denies every later Runtime write before a syscall. Individual Fence `stale` attempts remain internal; bounded exhaustion closes the operation/headroom through one ordinary sequenced failure Result before typed busy. Ordinary Audit append failure before a required synchronization attempt remains `audit_degraded` and retains the same Operation ID, owner, remaining headroom, and exact prepublication Effect or post-C19 dependent completion Effect for supervised continuation; it does not latch Storage Barrier Failure. There is no unchanged-state claim, same-session durability retry, failure marker or failure Audit record, Clean Shutdown Boundary, or explicit Daemon Instance Lock release. Before a trustworthy Store result there is no activation; a later Audit durability or pending-clear failure does not roll back the exact candidate already activated by C19, and the successor completes its exact pending evidence forward without recovering the live Effect.

Runtime Bundle creation is an offline read-only operation after current-Policy Offline Maintenance Authorization and while holding both locks and a matching Anchor. It rejects confirmed Cross-Authority Damage, pending publication, and any unverifiable committed boundary before output staging because no post-damage capture can be a Recovery Bundle.

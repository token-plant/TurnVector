# Run a Rust Daemon with a C++ Device Worker

Bootstrap owns two independent strict bounded canonical UTF-8 JSON artifacts: a Bootstrap Condition Model declaring mutual exclusions, implications, and check prerequisites, and a Bootstrap Action Decision Table whose rows reference that model. Together with the Compatibility Custody CI Policy and Bootstrap Semantic Change Declaration, these repository-owned artifacts use one versioned TurnVector canonical profile: no BOM, schema-bounded values, ASCII property names in bytewise lexical order, two-space indentation, LF separators and one final LF, direct non-control UTF-8 scalar values without normalization, `\"` and `\\` escapes for quote and backslash, lowercase `\u00xx` escapes for controls, canonical decimal integers without leading zeroes, and schema-defined array order. Their exact ASCII domains are `turnvector.bootstrap-condition-model`, `turnvector.bootstrap-action-decision-table`, `turnvector.compatibility-custody-ci-policy`, and `turnvector.bootstrap-semantic-change-declaration`. Root `format_version` starts at one, must equal the framed `u32_be(format_version)`, and changes only for incompatible schema or canonical-encoding changes, not ordinary semantic row or Policy-value changes. A repository `rust-toolchain.toml` pins the exact Rust release, Cargo.lock pins dependencies, source plus golden fixtures remain in Git, and that Rust tool is the sole writer and formatter; CI regenerates twice byte-for-byte, while C++ consumes generated constants and never implements another JSON writer. Compiler or tool changes receive ordinary reviewed fixture regeneration, while identity remains a function of exact canonical output bytes rather than executable or compiler digest. Every reader strictly parses, re-encodes, and requires byte equality. Each artifact identity is `SHA256(u32_be(domain_len) || domain || u32_be(format_version) || u64_be(byte_len) || exact_bytes)`. Generated identities remain build/status provenance only and do not alter the separately defined exact-file-byte Installation Policy identity.

Authenticated Bootstrap status contains Daemon Instance ID, a nonzero checked `u64` Bootstrap Evaluation Generation, exact Condition Model and Action Decision Table identities, and four independently bounded fields: the complete confirmed Condition Set, Blocked Bootstrap Checks, exactly one Primary Required Action, and at most eight Alternative Recovery Actions emitted by the same matched table row. A new Daemon Instance starts generation one and reuses it only while canonical bytes for both artifact identities, sorted typed inputs, check outcomes, selected actions, and prerequisite states remain equal; observation time and diagnostic text are excluded. Any included change checked-increments generation, while before `u64` overflow the process publishes no new status, exits, and lets the next Instance restart at one. All fields and each sorted unique Recovery Prerequisite conjunction come from one immutable evaluation. `met` means verified true, `unmet` safely false but externally satisfiable, and `blocked` unverified solely because of one named Blocked Check. The table emits every structurally possible route but omits a proved-impossible route; commands revalidate, and neither generation nor status grants authority. OR, NOT, nesting, free text, client inference, and duplicate action IDs are forbidden.

The generated Initialization Manifest Binary Maximum is computed from canonical field and count bounds and proven by a worst-case encoding fixture. Control Hello and authenticated status expose it together with the process-fixed Initialization Manifest Repair Effective Maximum, the lower of binary and current-Policy limits. The repair limit governs only externally submitted bytes: an intact Locator-selected Manifest remains valid and has no Readiness penalty merely because its length exceeds that Policy limit. A larger repair request returns non-retryable stable `manifest_repair_limit_exceeded` before Hashing or evidence copy and includes bounded typed detail containing `request_bytes`, `effective_max_bytes`, and `binary_max_bytes` only when the selected Control minor defines that variant and the effective capability set contains its distinct registered `manifest_repair_limit_detail_v1` ID. The reason requires Policy replacement plus daemon restart, grants exact Locator Hash no exemption, echoes no content or Hash, and creates no durable condition or Decision Table input.

Each Bootstrap Action Decision Table row declares one registered Primary Required Action and zero to eight distinct registered alternatives with exact conjunctive prerequisites. Generation enumerates every input reachable under the separate Condition Model and rejects zero or multiple row matches, unknown IDs, unreachable rows, unsatisfiable prerequisites, duplicate action IDs, an alternative equal to Primary, invalid prerequisite state, or non-canonical order. CI retains one golden output per canonical reachable vector and emits one complete semantic diff covering reachable-input, row, Primary, ordered Alternative, and every prerequisite ID/state/blocker change. Any behavior delta requires exactly one canonical Bootstrap Semantic Change Declaration under domain `turnvector.bootstrap-semantic-change-declaration`, permanently appended as `bootstrap/semantic-changes/<64hex-declaration-id>.json`, binding an ordered old/new identity pair for both Condition Model and Decision Table, the regenerated total-diff digest, and one reviewed ADR path. Genesis uses a typed `NO_PREDECESSOR` old variant for both artifacts rather than a fake Hash; afterward an unchanged artifact repeats its identity but at least one pair must change. The filename verifies exact bytes, and no-op, modification, deletion, split, absent, surplus, or mismatched declarations and unexplained byte/hash drift fail generation, while reviewed changes require no Runtime migration. Runtime severity, source order, Installation Policy, and plugins cannot alter output.

Qualification Lineage Reset fixes the Profile minimum at exactly 67,108,864 bytes and computes `max(67_108_864, policy_required_bytes)` with checked `u64` arithmetic; percentages and filesystem-relative fractions are invalid. Changing the binary floor or calculation changes Storage Capability Profile identity and therefore requires offline requalification plus explicit Storage Qualification Rebind, while a Policy-only increase changes only that operation's effective evidence. Against an already opened exact volume-root descriptor, the tool obtains `f_bavail` and `f_bsize` with `fstatfs`, rejects negative or unrepresentable values, and uses checked multiplication. Exact generated worst-case bytes still to write are added outside the margin. Before staging it checks the complete requirement; after the Reset Record and candidate Head are fully synchronized, it repeats the check for the margin plus bounded publication remainder immediately before Head publication. Failure leaves the old Head unchanged and any synchronized candidate orphaned. The Record binds the effective margin, both observations, and Installation Policy Identity; there is no logical record-count ceiling or deletion path.

Every Manifest staging target binds the exact filesystem UUID, 64-bit `ATTR_CMN_FILEID`, and object type obtained without following links; a regular file separately binds File Hash and must have `st_nlink == 1` both when the Manifest is created and immediately before prune. Qualification must prove both `VOL_CAP_FMT_PERSISTENTOBJECTIDS` and `VOL_CAP_FMT_64BIT_OBJECT_IDS`, otherwise Initialization and later prune are unsupported. The fixed-owner staging directory mode excludes untrusted concurrent writers. The command retains each parent descriptor and immediately revalidates no-follow identity, type, File Hash, and link count before `unlinkat`; this is not an atomic compare-and-unlink, and authorized same-UID or root mutation remains inside the Local Trust Boundary. `st_dev` may prove only a live same-volume relationship, while link count, path, name, timestamps, `st_gen`, and content equality cannot replace identity. Every failed report entry carries exactly one registry ID: 1 `identity_changed`, 2 `type_changed`, 3 `parent_unavailable`, 4 `directory_not_empty`, 5 `permission_denied`, 6 `io_failure`, or 7 `multiple_links`. A regular target with link count other than one is never unlinked; no force or skip exists, and after restoring `st_nlink == 1` the operator must rerun the complete parent, type, identity, File Hash, and link-count preflight from the beginning. Remaining classification follows the first definitive invariant.

When Initialization Provenance Missing and an independent Control finding coexist, Manifest repair remains primary. The daemon first compares request length with the process-fixed Effective Maximum and returns `manifest_repair_limit_exceeded` without Hashing, evidence copy, `PREPARED`, durable condition, or Decision Table mutation; it grants no exact-Hash exception. The response directs the administrator to replace Policy and restart before retrying. Only an in-limit request is Hashed, matched to the Locator, strictly parsed, and published. Intact selected provenance remains independently valid even when its current length is above the repair Policy limit.

A pending Rebind whose exact custody is absent or invalid selects Rebind Tool Custody Restoration as its Primary Required Action and returns qualifying new-ID Clone as an Alternative Recovery Action. Restoration runs under fresh offline authorization, verifies and synchronizes exact token-digest-matching bytes on the candidate-qualified Identity-root volume, and returns one bounded non-authoritative command result. It writes no Runtime Receipt, Runtime Audit Record, Anchor, Metadata, Control, or Publication Token byte; only the later exact Rebind resumer may change Runtime authority.

Every Qualification Lineage Reset Record, whether selected or orphaned, is retained permanently in installation custody. No Runtime or installation artifact-prune command, TTL, count limit, successful successor, or lineage replacement may delete it.

Pre-Locator prune never enumerates an unexpected directory child for reporting. After all Manifest-listed children have been processed, failure to remove the parent as empty yields only the stable typed reason `directory_not_empty`; no unknown name or content enters the bounded report, and later listed targets still run.

When Initialization Provenance Missing coexists with exactly one prerequisite authority failure, the daemon may expose only the one repair needed to make Initialization Manifest Repair viable: Metadata repair requires valid Control, Audit, and its ordinary prerequisites, while Audit or Audit Pointer repair requires valid Control, Metadata, and its ordinary prerequisites. Completion of that repair ends the maintenance session; a fresh Bootstrap must rederive all conditions before Manifest repair can begin. Damage to both Metadata and Audit is Cross-Authority Damage and permits only Clone from an already registered, independently valid Runtime Bundle. No command may compose, queue, or execute two repairs under one intent. If Locator Degraded is also present, Manifest repair precedes Locator Repair; after Manifest repair a fresh Bootstrap must succeed before Locator Repair is exposed.

The daemon's Manifest-repair interface accepts exactly one bounded raw byte string and has no claimed-Hash, Bundle-path, Bundle-source, or source-kind field. The daemon computes the File Hash and compares it with the unique Locator selection. A CLI may independently verify an entire Runtime Bundle, extract the exact selected Manifest bytes, and submit them through that same interface, but the daemon grants no authority to the Bundle location or wrapper provenance.

A pending Storage Qualification Rebind never changes its Publication Token when Rebind Tool Custody is missing or corrupt. Under fresh current-Policy offline authorization, an operator may reinstall only the exact token-digest-matching custody bytes on the candidate-qualified Identity-root volume; the tool fully synchronizes and revalidates the complete bundle before the same candidate executable resumes. Any unequal or rebuilt bytes are substitution and are rejected. If the exact bytes are unavailable, same-ID Rebind remains pending; the token is neither cleared nor rewritten, and recovery is limited to Clone under a new Runtime ID from an already existing valid Runtime Bundle.

Qualification Lineage Reset recovery never scans records. An explicit resume names exactly one Qualification Lineage Reset Record File Hash and, after current authorization and complete record revalidation, observes the fixed Head as old predecessor state, the record's exact candidate state, or a third state. Candidate completes idempotently; old state republishes the same candidate and barriers before rechecking; third state fails without selecting bytes. An invocation without a record hash starts a fresh reset with a new Lineage ID and record, leaving every unselected earlier reset record orphaned.

A pre-Locator Initialization Manifest exhaustively enumerates every staging file and directory with type and identity in canonical children-before-parent order. Prune uses only that list, performs no recursive enumeration, and never treats directory contents as implicit targets. An unexpected child makes the containing directory's result `failed`; the command still processes every later Manifest entry and reports the complete bounded outcome set.

The MVP runs as a long-lived local Rust TurnVector Daemon that owns separate permission-restricted Unix sockets for Data and Control Planes, Request State, Scheduler, Resource Governor, Audit Journal, and the sole Runtime Event Loop; it opens no network listener. It first validates and snapshots one Installation Policy, and any failure exits before sockets, locks, Bootstrap, or Service Liveness. Public socket paths include their protocol-family major version. A major upgrade therefore performs explicit drain and Graceful Shutdown, then coordinates replacement of daemon, Worker, and clients rather than translating protocols in one process.

Each runtime uses a stable container whose Daemon Instance Lock, Runtime Locator Record, permanently retained content-addressed Initialization Manifest directory, and Runtime Metadata Store remain outside its replaceable `current/` payload. The daemon holds the lock for its lifetime. The fixed Locator is one non-symlink regular file containing two independent fixed-size slots; each slot binds format, the same 16-byte Runtime ID, exact Initialization Manifest File Hash, creation-time qualification generations, and its own CRC. Initial publication builds both equal valid slots and uses `RENAME_EXCL` plus parent synchronization. One valid slot establishes that ID but reports Locator Degraded and forbids serving until explicit same-ID repair; two invalid slots or an absent Locator in an identity-bearing container are Locator Unrecoverable; two valid slots with unequal IDs or manifest identities are Identity Conflict. No command-line ID, identity-root scan, directory-name convention, Control row, or other Runtime authority can replace or choose a Locator. Every Bootstrap resolves the selected Manifest only at its canonical File Hash path and verifies its exact bytes; absence or corruption in an established Runtime confirms Initialization Provenance Missing without changing the Locator-established ID or suppressing independently obtainable findings. Before an offline Runtime Bundle creation, registration, Store Migration, Runtime Restore, Runtime Clone, qualification rebind, or archived-artifact prune may acquire the container lock, the tool snapshots the fixed-path Policy, verifies its Installation Policy Identity, and proves its credentials are allowed. Only then, while the daemon is absent, may it read the Locator, acquire the matching Runtime Identity Lease, and validate the Anchor. Explicit live repair instead uses the non-ready daemon with no Worker. A separate installation-fixed identity root contains leases, Anchors, immutable qualification records, and one fixed two-slot Storage Qualification Head per filesystem UUID and Storage Capability Profile without a central mutable database. Each Head payload carries the random current Storage Qualification Lineage ID in addition to that lineage's checked generation. The Anchor keeps its existing two alternating format-neutral slots and alone binds the exact currently authorized Runtime and Identity-root qualification records in addition to history, Audit, ownership, recovery, role-block, and Publication Token state.

Every initialized daemon holds the Runtime Identity Lease for its lifetime and may continue only after Locator, selected Anchor, Control, Metadata, and Audit identities agree. A merely occupied lease or two valid unequal Locator slots is Identity Conflict. Both invalid Locator slots are Locator Unrecoverable and never authorize Anchor lookup from other bytes. After Locator publication but before initialization completes, a missing Anchor is legal only when the Locator-selected immutable Initialization Manifest and every named candidate verify; that Manifest authorizes creation of the first Anchor and forward completion. Otherwise both invalid Anchor slots are Anchor Unrecoverable: neither Control nor a Bundle recreates the same-ID Anchor, and only Clone may continue under a new ID. For an established Runtime whose Locator, Anchor, and current qualification agree, Initialization Provenance Missing still permits `CLAIMED`, mandatory rollback recovery needed to obtain independent Store findings, and only a narrowly authorized live-repair executor. It forbids Worker launch, Data Plane service, ordinary Control mutations, and every unrelated maintenance intent until exact Manifest provenance is restored. Initialization Manifest Repair accepts only operator-supplied bytes whose exact File Hash equals the established Locator selection; a typed missing-file observation or the complete corrupt original becomes immutable Repair Evidence. The operation binds that observation or predecessor, exact candidate, Receipt, and Pending Audit Envelope in Anchor `PREPARED`; create-if-absent publishes into a missing canonical path, while atomic same-volume exchange publishes over corrupt bytes and retains the displaced object, and both paths synchronize the parent directory. Anchor `COMMITTED`, exact standalone Receipt synchronization, Audit-head advance, pending clear, and `COMPLETED` follow. Native inspection accepts only the bound predecessor observation or bytes and exact candidate, never chooses alternate content or changes the Locator, Runtime ID, Manifest Hash, or creation provenance. A Locator Degraded daemon may expose Locator Repair through current-Policy Maintenance Capability only after the sole good slot, Lease, Anchor, current qualification generations, Control, Metadata, and Audit all verify. The operation preserves the complete observed Locator as Repair Evidence, builds a candidate by copying the sole valid slot unchanged into both positions, and binds predecessor and candidate File Hashes, evidence, Receipt, and Pending Audit Envelope in Anchor `PREPARED`. Atomic same-volume exchange plus parent synchronization publishes the candidate while retaining the displaced bytes; Anchor `COMMITTED`, exact standalone Receipt synchronization, Audit-head advance, pending clear, and `COMPLETED` follow. Recovery accepts only exact predecessor or candidate File Hash, never alters Runtime ID, Manifest Hash, or creation provenance, and treats any third state according to its observed identity condition rather than choosing bytes. The daemon remains non-ready with authenticated status and no Worker for every identity condition. Runtime Bundles remain offline-only; Registration stores only Bundle Hash and lineage proof, never a path or copy, and ordinary Readiness does not depend on locating those bytes. Cross-Authority Clone accepts operator-supplied bytes only after they verify to the exact registered hash.

New identity establishment is the sole exception to ordinary Anchor-first publication. Initialization and Clone fully build and synchronize candidate `current/`, Metadata, Audit continuation and root Segment, first Anchor payload, and one immutable Initialization Manifest before publishing anything. The Manifest binds Runtime ID, Locator parameters, every post-Locator candidate identity and File Hash, selector value, creation-time qualification generation, Policy identity, Operation ID, and Epoch Open bytes; its own File Hash is then embedded in both Locator slots, so it never recursively hashes Locator bytes. The Manifest is published at its canonical File Hash path in a dedicated stable directory before Locator publication, remains permanently retained and ineligible for artifact prune, and is reverified on every later Bootstrap. Publishing the two-slot Locator with `RENAME_EXCL` is the point of no return: before it, all candidates are non-authoritative Initialization Staging; after it, Bootstrap acquires the named Lease, verifies only that Manifest, creates the first Anchor `PREPARED`, and publishes `current/`, then the Metadata authority directory, then the Audit pointer through create-if-absent before Anchor `COMMITTED`. Each selector is either absent or exactly the Manifest candidate; a third value never authorizes substitution, and post-Locator recovery never aborts or selects another candidate. Authorized offline prune of abandoned pre-Locator staging acquires the container lock and proposed Runtime ID Lease, then completes authorization, exact-Manifest, absence, object-type, and full-target preflight before deleting any target. It then attempts every Manifest-enumerated target in canonical order despite individual failures, never scans or adopts candidates, never removes the Lease file, and rolls nothing back. A target result is exactly `removed`, `already_absent`, or `failed`, and overall success means every target is absent. The command returns one bounded non-authoritative Pre-Locator Prune Report containing the Manifest Hash, complete target list, and every result, but persists no Runtime Receipt, Audit record, operation tombstone, or replacement authority; a crash returns no report, and an authorized rerun revalidates all prerequisites and recomputes the complete result. Established runtimes then use the ordinary protocol: `CLAIMED` precedes recovery writes; candidate and staging synchronize; Anchor `PREPARED` precedes kind-specific publication; Anchor `COMMITTED` precedes strong Audit and acknowledgement. A SQLite authority publish consists of its successful transaction commit followed by explicit synchronization of the database parent directory; external state cannot advance between those two barriers.

The daemon spawns one C++ Backend Worker over an inherited private socketpair. That Worker must acquire a lifetime Device Ownership Lease and complete nonce, Daemon Instance ID, and protocol negotiation before owning MLX state. An offline qualifier holds the installation qualification lock and performs isolated real syscall probes for one volume. For the exact filesystem UUID and Profile, its fixed two-slot Storage Qualification Head binds a random Lineage ID; two valid slots are generation-compared only when that ID agrees, and the highest valid checked lineage-scoped generation supplies the append predecessor. One valid slot permits one normal successor append that restores redundancy, while different valid Lineage IDs, no valid slot, equal-generation disagreement, or a broken selected predecessor chain blocks ordinary qualification. The new immutable record binds that Lineage ID and predecessor and is fully synchronized before the Head advances; a record left unselected by a crash is orphan staging that no scan, later append, Bootstrap, or Head recovery adopts automatically. When no valid Head slot, different valid Lineage IDs, or equal-generation disagreement makes the allocation lineage unusable, an explicit offline Qualification Lineage Reset under the same lock atomically publishes two equal `NO_PREDECESSOR` slots with a new random Lineage ID at the fixed Head path. It preserves every old and orphan record and every Runtime's exact bound references, performs no record scan or adoption, and requires the next qualification to run the real probes before creating the first record in the new lineage. Each immutable record also binds the exact 16-byte filesystem UUID returned by `getattrlist(ATTR_VOL_UUID)` on an already opened volume root, exact OS build, TurnVector build, Profile identity, complete probe results, and its lineage-scoped predecessor; history is retained. Paths, mount points, volume names, device nodes, and session-local `fsid` values are never persistent identity, while descriptor-relative `statfs` relationships may prove that required objects currently share a filesystem. The Storage Capability Profile identity binds one build-owned `EINTR` completion deadline used unchanged by both these probes and every Runtime barrier; Installation Policy cannot shorten, extend, or replace it. The Initialization Manifest permanently records creation records, while the Identity Anchor alone binds exact currently authorized records for both Runtime Authority and Identity-root volumes. An OS, binary, Profile, or filesystem-UUID change therefore requires offline requalification followed by explicit Storage Qualification Rebind before startup, never a daemon write probe, Locator rewrite, or implicit latest-generation selection. Before Rebind `PREPARED`, the exact candidate TurnVector build places a self-contained tool bundle in installation recovery custody outside every Runtime; the Publication Token binds its content digest and never its path. That bundle is immutable and deletion-forbidden until the Rebind reaches `COMPLETED`; after completion only an explicit cleanup may remove it. This exact candidate-build offline executable is the sole Rebind executor and resumer under current-Policy offline authorization, both locks, and a matching Anchor; predecessor records prove the currently bound state but authorize no write, while exact candidate records govern every Rebind barrier and resulting byte. Before `PREPARED`, failure changes no Runtime authority. After `PREPARED`, a crash or barrier failure leaves the exact token, returns `outcome_indeterminate` when a response remains possible, performs no cleanup or later write, and exits; only an explicit invocation of that same candidate-build tool may inspect predecessor/candidate state and continue the fixed intent. Daemon Bootstrap reports the pending Rebind and never reconciles it or writes `CLAIMED`. A completed tool invocation validates both record sets plus the complete Receipt and Pending Audit Envelope, installs the candidate set through Anchor `COMMITTED`, strongly synchronizes the standalone Receipt, advances the Audit head, clears pending evidence, and never changes Runtime ID or creation provenance. Bundle destinations are independently probed for each capture but are not Runtime-bound records. Bootstrap verifies the Anchor-selected records and current relationships read-only. Missing, stale, or mismatched current evidence is Storage Capability Missing. A required durability syscall returning `EINTR` may re-invoke only that identical syscall on the same open descriptor, with no semantic state advance, until the Profile-bound monotonic deadline; deadline expiry or any non-`EINTR` error confirms Storage Barrier Failure. In a daemon session that condition immediately stops the Worker and all further Runtime writes, permits no same-session operation-level retry, retains both identity locks with authenticated read-only status until OS signal, and creates one structured in-memory Barrier Failure Observation containing session, optional Operation ID, authority kind, phase, registered object role, syscall, errno, elapsed time, deadline, and `outcome_indeterminate`. Authenticated status exposes it and the daemon emits best-effort structured stderr and metrics, but writes no Runtime Audit record, failure marker, or clean release. After signal exit, the next Bootstrap derives every condition again from durable bytes and performs no automatic requalification or manual-clear check.

Initialization Manifest Repair preflight accepts either two agreeing valid Locator slots or the sole valid slot of Locator Degraded because both uniquely establish the same Runtime ID and Manifest File Hash. It additionally requires the established Anchor, both exact current Storage Qualification Records, usable Runtime Metadata publication staging, and writable verifiable Audit authority; Control must have completed its independent inspection but a Control Repair or Control-schema Migration No Path finding does not block this identity-only repair and remains reported. Identity Conflict, Locator or Anchor Unrecoverable, Storage Capability Missing, Storage Barrier Failure, Metadata Repair Required, Audit Repair Required, or Cross-Authority Damage rejects the repair before evidence copy or `PREPARED`.

Pre-Locator prune retains already-opened parent-directory descriptors and uses descriptor-relative no-follow inspection and removal only. Immediately before each removal it rechecks the exact Manifest-bound target type and identity against preflight; a missing target becomes `already_absent`, an unchanged target is removed, and any symlink, special object, replacement, or other identity change becomes `failed`. That per-target failure never skips a later canonical target or rolls an earlier result back.

Every Runtime Bundle includes the exact current Locator-selected Initialization Manifest bytes plus their File Hash as immutable source provenance. Restore requires that File Hash to equal its target Locator selection and never uses Bundle bytes to change that Locator or Manifest; Clone retains the source bytes only in Bundle lineage evidence, creates a distinct destination Manifest under the new Runtime ID, and binds the source Manifest File Hash as lineage rather than destination authority.

A broken selected qualification-record predecessor chain is reset-eligible under the same explicit offline authorization; it is never repaired by adopting an orphan. Before replacing an unusable Head, the reset command preserves exact valid-slot hashes and typed invalid-slot observations, any selectable prior Lineage ID, filesystem UUID, Profile identity, new random Lineage ID, Installation Policy Identity, and tool build in one canonical content-addressed Qualification Lineage Reset Record. It fully synchronizes that immutable record before atomically publishing two equal `NO_PREDECESSOR` Head slots that bind its File Hash and new Lineage ID, while retaining all older records and creating no Runtime Receipt or Audit record.

Rebind Tool Custody resides on the candidate-qualified Identity-root volume and contains only strict fixed-owner regular files with bounded modes: the candidate executable, every non-system dynamic dependency, and one canonical manifest covering the complete set. Symlinks and special files are forbidden. Immediately before every first execution or resume, the offline entry point reopens without following links, verifies ownership, mode, manifest, every File Hash, and the token-bound whole-bundle digest; any mismatch refuses execution rather than trusting a path or opportunistic rebuild.

Rebind Tool Custody stores executable bytes only in the installation recovery area. Git may retain their content digest, source, and exact build recipe, but no executable bundle; neither a Git checkout nor a path string can substitute for the digest-bound self-contained bundle selected before `PREPARED`.

Bootstrap verifies only bytes that their governing formats allow it to interpret and returns four bounded fields: every confirmed condition, every blocked check with its stable reason and prerequisite conditions, exactly one Primary Required Action, and a deterministic bounded list of Alternative Recovery Actions with exact prerequisites. Conditions, blocked checks, required actions, and recovery prerequisites each use a distinct repository-tracked append-only `u32` registry: zero is invalid, published IDs are never reused, removed meanings remain reserved, generated protocol constants derive from the matching registry, and IDs never cross namespaces. Blocked checks are sorted by registry ID rather than discovery order. The repository-tracked Bootstrap Action Decision Table matches the complete condition set and explicit prerequisite availability to exactly one registered action; build validation rejects unknown IDs, unreachable rules, uncovered reachable inputs, or multiple matches, and selection never hides the other fields. Supported older Anchor, Store, active Hash, or active Audit formats require explicit transition; an unsupported or explicitly retired format reports Migration No Path, and bytes are never reinterpreted as corruption.

Storage Capability Missing leaves both locks held but writes no new `CLAIMED`, Anchor, Store, Metadata, Audit, staging, or cleanup byte and starts no Worker or Runtime Event Loop. The daemon exposes only Service Liveness and authenticated read-only status until OS signal; after daemon exit, an authorized offline Bundle capture may read the already committed authorities under both locks without requiring the missing write capability, but every output file and manifest must receive its target-volume durability barriers before atomic publish. The MVP offers no same-ID relocation or Restore to a different path: a valid Bundle is cloned onto a capable volume under a new Runtime ID. If required sequence reservation is impossible instead, Sequence Exhausted starts no Worker or Runtime Event Loop, retains both locks, writes no Audit, and serves only read-only Liveness/status until OS signal. Storage Barrier Failure uses the same lock-retaining liveness shell after terminating the Worker and abandoning every further Runtime write; OS-signal exit attempts no failure marker, Clean Shutdown Boundary, Anchor release, Audit append, or other durability operation. The following process performs ordinary startup and Bootstrap, rederives state from exact bytes, and requires requalification only when those checks independently confirm Storage Capability Missing. Otherwise valid state still requires the full storage profile, exact Initialization Manifest, complete publication and Audit reconciliation, exclusive ownership, Worker handshake, and fresh Resource Evidence. Graceful Shutdown strongly synchronizes a Boundary binding the session, predecessor Audit Head Hash, and every unused sequence through high-water before attempting `CLEAN_RELEASED`; if that Anchor write fails, the next Bootstrap accepts the exact closed tail and makes only its own claim.

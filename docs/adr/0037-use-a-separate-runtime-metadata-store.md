# Use a Separate Runtime Metadata Store

This decision applies to the Integrity Serving Profile. The P0 Serving Profile has no Runtime Metadata authority, Metadata repair, Bundle, Restore, or Clone capability; their absence cannot block Service Readiness under that profile and must be reported as unsupported rather than silently emulated.

Ordinary exact Metadata repair may resolve a conflicting reappeared saturation marker only when two fresh Jobs prove one copy digest-valid and identity-bound and the other invalid. The valid lower bound may restore current `AT_LEAST_MAX`, but Runtime Metadata permanently retains both observations, the Conflict Incident, prior loss and intervening `SATURATION_CONTINUITY_UNKNOWN`; repair never backfills coverage or creates Control authority.

When a previously lost saturation marker reappears under the same identity with conflicting valid bytes, Runtime Metadata records a nonauthoritative marker-integrity incident, retains both copies and the prior loss, and keeps current status `SATURATION_CONTINUITY_UNKNOWN`. It selects neither latest nor preferred bytes and does not escalate the conflict into a Repository Root Hash Incident; only ordinary exact Metadata repair may later qualify a current lower-bound marker without erasing the historical gap.

An exactly reappeared and verified saturation marker may restore current `AT_LEAST_MAX` status, but Runtime Metadata permanently retains the intervening `SATURATION_CONTINUITY_UNKNOWN` interval. Reappearance never backfills diagnostic coverage, erases the loss status or creates an authoritative count.

If the compact saturation marker is missing or unverifiable, Runtime Metadata reports `SATURATION_CONTINUITY_UNKNOWN` with the last verified Audit Cut and runtime boundary. It never substitutes zero, a reconstructed count or raw-log replay, and it changes no authority by itself while ordinary Metadata integrity handling remains applicable.

The Runtime Metadata Store retains only a compact nonauthoritative Restart Continuity Marker for a saturated post-Cut diagnostic-drop counter: Audit Cut identity, `AT_LEAST_MAX`, its maximum lower bound, prior runtime identity and explicit discontinuity. It stores neither raw diagnostics nor an authoritative count, never enters Control State or Audit lineage, and cannot imply complete continuity after restart.

Under Initialization Provenance Missing, Metadata repair is exposed as a Manifest-repair prerequisite only when Control, Audit, and every ordinary Metadata-repair prerequisite independently verify. Successful Metadata repair ends that daemon session; a new Bootstrap must confirm Metadata and then select Manifest repair. If Audit is also damaged, the condition is Cross-Authority Damage and neither sequential nor compound same-ID repair is offered.

The stable runtime container holds a dedicated Metadata authority directory outside `current/`; it contains one local SQLite Runtime Metadata Store in `journal_mode=DELETE`, `synchronous=FULL`, `fullfsync=ON`, and `temp_store=MEMORY`, plus only the exact regular-file basenames recognized by the current binary from the independent append-only `u32` Metadata Role Registry. WAL mode and its WAL/SHM roles are not part of the MVP authority image. The registry classifies the main database as persistent identity and the DELETE-mode rollback journal as volatile recovery evidence: the journal is copied when present but never enters Metadata Store Image Hash. Locks, the Runtime Locator Record, permanent Initialization Manifest directory, installation qualification registry, and repair staging remain outside the Metadata authority directory. Every registry entry fixes one basename, persistent or volatile classification, inclusion in identity hashing, evidence-copy requirements, and permitted repair treatment; zero is invalid, identities and basenames are never reused, removed entries stay reserved, and plugins or filesystem heuristics cannot extend it. Its catalog authority consists of immutable Metadata Catalog Generations containing lineage availability, repair-evidence availability, and explicit unrecoverable-metadata facts, with one atomic current-generation pointer. Authority Publication Staging and count- and time-bounded Maintenance Operation Tombstones occupy separate monotonic tables and are never copied into or rewritten with a catalog generation. Normal catalog publication inserts and synchronizes a complete candidate, records staging, writes Anchor `PREPARED`, atomically advances only the catalog pointer, explicitly synchronizes the database parent directory, and only then writes Anchor `COMMITTED`; native inspection identifies exact predecessor, candidate, or third state. Non-current catalog generations are retained under count and total-byte limits, but current and every Anchor- or non-terminal-staging-referenced generation are exempt; only an unreferenced predecessor of a completed operation may be reclaimed. One bounded executor owns one connection to exactly this main database under both locks. `ATTACH` and `DETACH`, on-disk temporary databases, cross-database transactions, and super-journals are forbidden; bounded temporary work may use memory only. Scheduling never queries the store, it is excluded from Semantic State Hash, and damaged facts enter Metadata Repair Required with no Device Executor or automatic empty store.

Runtime Bundle manifests contain only the identity-scoped lineage and repair-evidence summary plus referenced immutable evidence bytes needed to validate the capture; they never copy the Runtime Metadata Store itself. Cross-Authority Damage forbids a new capture because Metadata and Audit cannot certify one boundary; only operator-supplied bytes verifying to the Bundle Hash selected by the Anchor's pre-damage Recovery Bundle Registration may feed its Clone. Registration stores no path or copy and its external availability is not ordinary Readiness. Restore first requires every target operation terminal, then preserves that store in place on the same Runtime Authority Volume and reconciles destination publication state. Clone creates a fresh store under new identities on a destination volume whose exact qualification generation was verified before any ID or staging creation; source Operation IDs, catalogs, tombstones, and maintenance history never cross. Metadata schema migration is explicit and forward-only through a registered migrator that understands both schemas. Before any state change it verifies the complete Storage Capability Profile, including same-filesystem atomic directory exchange, SQLite full-fsync behavior, post-commit database-parent synchronization, `F_FULLFSYNC` for staged authority files, and namespace parent synchronization; otherwise it requires capability restored on that volume or old-binary Clone of a pre-upgrade Bundle under new identities and offers no same-ID relocation, multi-rename, ordinary-fsync, or temporary-pointer fallback. On a supporting volume it writes `PREPARED` in the predecessor, carries that same operation, monotonic tables, immutable catalog generations, and current pointer into a fully synchronized replacement before publishing it under a fixed Anchor token and continuing in the candidate. It uses no recursive third journal. Because Restore preserves target Metadata and location, downgrade requires in-place Restore or the old binary to Clone a pre-upgrade Bundle into a new Runtime rather than reverse-migrating the same Runtime ID.

Explicit Metadata Repair instead runs through the live but non-ready daemon's maintenance executor with no Device Executor and a connection-scoped Maintenance Capability authorized by the current Installation Policy. The trusted tool creates the Operation ID under a global non-reuse obligation, but repair never depends on staging in the damaged store. Under both locks the daemon first inventories every object in the dedicated authority directory without assigning meaning by suffix. It derives effective count and byte limits from the lower of binary hard maxima and the Policy snapshot bound when the operation begins, verifies the filesystem safety margin, proves the complete Receipt fits, and binds Installation Policy Identity plus effective limits into Intent Hash and Receipt before copying into Operation ID-bound Repair Evidence Staging. Every resume is authorized by the current Policy while retaining those bound semantics and limits. Capacity failure begins no copy or `PREPARED`; an interrupted recognized-role copy remains non-authoritative, Bootstrap reports but never adopts or deletes it, the same intent may resume it, and another operation leaves it for explicit prune.

Only registry-recognized regular-file roles may form a replacement authority image. Bootstrap inventories them read-only before any Store open; first observation of an unknown basename, symlink, special file, or registered role unsupported by the current binary reports conditions but cannot itself copy evidence or publish a Metadata Role Block. Once Locator, exact Anchor-selected qualification records, and an established Anchor verify, the daemon writes `CLAIMED` even when Initialization Provenance Missing independently blocks Readiness. It completes Control open and rollback recovery first and then Metadata so both independent results remain available for the narrow live-repair session; no Device Executor, ordinary Control mutation, unrelated maintenance intent, or service is allowed while that condition remains. A Control durability-barrier failure after same-descriptor `EINTR` completions reach the build-owned Storage Capability Profile deadline instead confirms Storage Barrier Failure and blocks Metadata open when it could require recovery writes, because that session may issue no further write. Any Metadata hot-journal rollback, main-database synchronization, journal deletion, and database-parent synchronization belongs to the new session; a remaining failure confirms the same condition and receives no same-session operation-level retry. The daemon requests Device Executor Shutdown, retains both locks, and exposes authenticated read-only status containing a structured in-memory Barrier Failure Observation with session, optional Operation ID, authority kind, phase, registered object role, syscall, errno, elapsed time, deadline, and `outcome_indeterminate` until OS signal. It emits best-effort structured stderr and metrics but attempts no Runtime Audit record, failure marker, or clean-release write; the next process derives state anew through ordinary Bootstrap. An explicit operator command under current Maintenance Capability starts the irrevocable Block path. The daemon synchronizes every obtainable object plus a canonical observation manifest and exact Pending Audit Envelope; change or disappearance after that authorized capture begins becomes explicit loss evidence and does not cancel the Block. Anchor `PREPARED` binds the immutable evidence, candidate Block identity, exact Audit record identity, operation, intent, and Installation Policy Identity. Anchor `COMMITTED` installs the Block and pending-envelope reference first; automatic Bootstrap recovery may then write only those exact Audit bytes, verify their identity, advance the Anchor head, and clear its token without another operator decision. The current binary cannot delete, move, rename, prune, or override the unresolved Block, even when the original or captured bytes later disappear. That state confirms Metadata Repair Required and also Migration No Path when the binary lacks the role; action precedence chooses no-path while preserving both confirmed conditions. A compatible binary removes only the no-path condition and may resolve the Block through the role's registered bounded repair semantics; Cross-Authority Damage instead permits only Clone from the exact Anchor-registered Recovery Bundle.

Initialization Manifest Repair uses this Store's ordinary monotonic publication staging and therefore requires its schema, current catalog, staging area, and durability behavior to verify after mandatory rollback recovery. A Control Repair or Control-schema Migration No Path result remains an independent finding and does not block Manifest repair, but Metadata Repair Required, an unresolved Metadata Role Block, Audit Repair Required, or Cross-Authority Damage does.

Without an unresolved Block, repair verifies the complete Storage Capability Profile before ordinary `PREPARED`; absence changes no state and permits no relocation, multi-rename, durability downgrade, or pointer fallback. For native identity, the predecessor's registry-classified persistent roles are represented by a canonical ordered manifest of role IDs and typed File Hashes; a present rollback journal is copied as volatile evidence but excluded from the image identity. The candidate completes rollback recovery in isolation, commits and closes with no live journal, and fully synchronizes its exact registered role set, whose canonical manifest yields its Metadata Store Image Hash. Filesystem paths, inodes, logical-row hashes, and unregistered SQLite naming conventions never identify either side.

The replacement is constructed solely from the selected Anchor, authoritative Control, verified Audit, and explicitly verified retained artifacts. Its first immutable catalog generation records reconstructed facts, preserved original artifacts, and every missing or unverifiable fact as unrecoverable; its separate monotonic area already contains the operation at `PREPARED`, which promotes the complete synchronized staging set to immutable Repair Evidence. A fixed Anchor token names predecessor and candidate Metadata Store Image Hashes. Native publication uses same-filesystem atomic exchange of the complete dedicated Metadata authority directory followed by parent synchronization; main-database-only or multiple-rename replacement is forbidden because an old rollback journal could contaminate the candidate or expose no stable publication point, and the displaced directory remains Repair Evidence. Anchor `COMMITTED` makes recovery forward-only. The daemon strongly synchronizes the standalone Metadata Repair Receipt before `AUDITED`, pending clear, and `COMPLETED`; neither completion nor abort deletes Repair Evidence. It becomes prune-eligible only when its owner is terminal and no Anchor token, Recovery Bundle Registration, unresolved Metadata Role Block, selected or retained Audit Continuation, retained Runtime Bundle, current Metadata Catalog Generation, or non-terminal staging references it; a successor catalog and durable prune Receipt record unavailability before file deletion. If Metadata and Audit are both damaged such that neither can verify repair of the other, it reports Cross-Authority Damage, preserves all artifacts, and refuses every prune, sequential or compound live repair, same-ID Restore, and new Bundle capture. Only Clone of the exact registered Recovery Bundle into a new Runtime ID may continue.

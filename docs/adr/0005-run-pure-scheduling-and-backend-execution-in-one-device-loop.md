# Run Pure Scheduling and Backend Execution in One Device Loop

The Rust TurnVector Daemon owns one dedicated Device Executor OS thread. On that thread, the Runtime Event Loop exclusively owns one deterministic synchronous Runtime Core and the statically linked C++/MLX Adapter. Bootstrap initializes the Core's first expected Event Sequence after Audit Reconciliation has written any required Crash Tail Boundary; from there, boundary inputs are validated into Domain Types, assigned strictly contiguous Event Sequence and daemon Monotonic Time, and passed one at a time to `Core::handle(event)`. The Core stages the complete candidate state or controlled delta, ordered outcomes, and Effects, verifies every production Core Invariant, and atomically commits only on success; failure preserves the prior state and exposes no Effect. For a Backend Effect, the Event Loop calls the Adapter directly on the same thread, synchronizes the bounded operation, and feeds its in-memory Effect Result back before another Turn begins. A result that remains Runnable authorizes no inline continuation: after its Receipt transition and every earlier sequenced event, the Core forms a fresh Scheduling Snapshot and Turn Plan, so a Prefill Chunk cannot conceal a full-prompt loop. There is no per-Turn channel, task wakeup, serialization, socket, or process boundary. External I/O threads may enqueue bounded coarse control events or set certified cancellation and safety signals, but they cannot mutate Core state or call MLX. An unexplained in-run sequence violation or invariant failure enters global Core Fault, while an explicitly bounded unrecoverable reserved tail declared across a crash does not. Legal state conflicts return audited Domain Rejections. Non-Backend I/O Effects carry Operation IDs, generations, stable order, and explicit dependencies; independent work may execute concurrently without deriving semantic order from completion timing. Every completion returns as an Effect Result Core Event, and duplicate, late, unknown, or generation-mismatched results never reapply state. The Core itself performs no I/O, async work, clock reads, serialization, callbacks, or MLX calls.

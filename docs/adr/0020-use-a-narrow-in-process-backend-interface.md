# Use a Narrow In-Process Backend Interface

The active Owner-Thread Support Budget identity includes finite per-operation/pool Support Start Count Bounds and their fixed physical start-credit capacities. No Backend Effect creates, funds, rebinds, or converts support capacity. The sole Core Support Charge Ledger owns Support Operation Obligations, typed Support Funding Claims, request Support Outstanding Credit Vectors, lifecycle reserves, and active charges. Immediately before preparation, `begin_support` either atomically creates one typed Ordinary Reservation Claim and starts its one currently legal matching obligation and physical credit, or moves exactly one pending obligation and its one physical credit into one active charge, enforcing every applicable half-open count bound. One batch/model-scoped Backend call has one obligation and one physical credit while each affected request contributes one exact typed claim: an Admission-reserved initial claim or an entitlement-vector claim; unstarted obligations may split, merge, rebind, or close with exact physical-credit, funding-claim, and call-scope conservation, and active scope/funders freeze. Exhaustion returns before Effect issuance. The active record, consumed credit, and linked claims remain retained through the Catalog Retention Horizon, and the Event Loop and Backend own no counter, allocation, or refund path.

Runtime Overhead Catalog entries reference only Daemon-Core-bound Lifecycle Evidence Tables for lifecycle operations, sequenced Core events, and local-stale disposition. Request Certification Case Bound Tables bind the outer daemon build later and are never Catalog inputs; the two terms and authority graphs are disjoint.

The daemon statically links one C++/MLX Adapter and invokes it only from the dedicated Device Executor owner thread. The Backend Interface is a narrow in-process seam, not a transport: no socketpair, Protobuf frame, capability handshake, message sequence, correlation ID, serialization, or per-Turn queue lies between Scheduler selection and MLX execution. Its complete P0 operation family is:

```text
initialize(control_view)                        -> BackendInitialization
describe_model(registration)                   -> RawModelDescriptor
describe_request(request)                      -> RequestDescription
materialize_request(description, reservation) -> MaterializationResult
release_request(request, reason, control_view) -> RequestReleaseResult
form_candidates(eligible, hard_constraints)   -> FormationResult
execute_turn(plan, control_view)               -> TurnResult
observe_turn_receipt(receipt)                  -> CostProfileUpdate
execute_exclusive(operation, control_view)     -> ExclusiveResult
transition_residency(operation, control_view)  -> ResidencyResult
sample_backend_resources()                     -> BackendResourceSample
shutdown(control_view)                         -> ShutdownResult
```

Every call is sequenced on the one owner thread; Backend operations never overlap. Each mutating Effect is invoked once and synchronizes before returning its typed result. Before initialization, a build-generated daemon-embedded Backend Bootstrap Manifest binds the expected complete Backend Capability descriptor, Backend Resource Signal Contract, and complete Backend Operation Bound Set identities plus the externally certified initialization entry; the daemon verifies it and starts the pre-call watchdog from that bound. The daemon separately selects one startup candidate Owner-Thread Support Budget, Sequenced Event Interference Bound, and Stale Plan Disposition Bound from its canonical embedded Runtime Overhead Catalog by exact Daemon Core Build, complete active Configuration Snapshot, stable platform facts, expected Backend descriptors, lifecycle/span schema, horizons, pools, and Lifecycle Evidence Tables; if no exact entry exists, startup fails. Initialization returns its complete versioned Backend descriptors, whose identities and contents must match the Manifest before any later call. A daemon-owned pre-activation matcher then completes Lifecycle Overhead Qualification against every returned identity before activating all three descriptors or making the first support call. For a later Configuration successor, that matcher is the sole selector of one exact Catalog entry against fresh stable facts and the unchanged returned identities and returns an immutable witness binding the proposed Configuration, selected descriptors, facts, and witness generation; Core only validates identity/current generation, carries ledger state, and activates that exact witness after committed publication. Neither path grants request Certification Applicability or Backend authority. A trustworthy initialization failure strongly rolls back all Backend root ownership before return and is not retried in the same process; missing that safe point fail-stops the process. A nominal success whose evidence mismatches the Manifest or startup qualification is untrusted live state and fail-stops without another Backend call or raw deallocation, while a missing or drifted successor qualification rejects that proposal before publication. The Backend does not authorize its own expected value, Catalog, or Support Budget. A Receipt-producing `execute_turn` direct-call interval is Engine Service; a pre-execution Plan Rejection interval is Runtime Overhead and charges no Model Ledger. `transition_residency` is separately gated Residency Service, and `execute_exclusive` runs only with shared dispatch paused.

From successful initialization until immediately before shutdown, describe, materialize, release, Candidate Formation, accepted-Receipt observation, and resource sampling consume the versioned Owner-Thread Support Budget according to a closed pre-ready/ready/evidence-degraded-or-recovery/drain matrix. Each operation has an independent direct-call watchdog and one complete daemon envelope beginning with either typed Ordinary Reservation Claim, obligation, credit, and active-record creation or, after any causal predecessor envelope ends, one standalone `begin_support` transition, and continuing through preparation, direct call, result validation, accepted Core transition, and immediate in-memory Effects. Core alone owns reusable Future Turn Support Entitlements with finite Support Outstanding Credit Vectors, operation obligations, lifecycle reserves, and active charges. Admission obtains actual initial-Materialization, initial-Candidate-Formation, and release obligations plus the complete request vector. Each Turn Plan creates one shared Receipt-observation obligation, one conditional continuation-formation obligation, and the mutually exclusive rejection/local-stale formation obligation; each is jointly funded by all members and carries one distinct physical credit. The continuation record remains a first-class unstarted ledger entry whose credit, claims, vector slots, storage, interference headroom and carry are occupied from Plan creation until observation moves it to pending or typed-impossible close. Cancellation may atomically split, merge, rebind, or close only unstarted obligations and funds terminal membership-change formation when required; active funders remain frozen. Before a load Effect, Core reserves the bounded post-load description-obligation set; before Receipt observation, its obligation carries the bounded post-update description set. Lifecycle qualification creates the first safety-sample obligation before readiness, and the sole trigger maintains the next obligation before evidence expiry. No operation allocates capacity after its causal trigger has made work mandatory. The Catalog Retention Horizon, not only the active Budget horizon, controls charge, credit, and linked vector-claim expiry. The Event Loop reports measurements but owns no ledger. A watchdog or complete-envelope excess invalidates Lifecycle Overhead Qualification and fail-stops before another Backend call; observation never widens a Catalog entry. Initialization precedes the support lifecycle and shutdown follows it.

The entitlement separately reserves vector capacity for terminal cancellation-membership-change formation. Receipt, rejection, local-stale, cancellation, and support Result transitions may only mark a successor obligation pending, rebind an unstarted scope, or close it on typed impossibility. After the complete predecessor envelope ends, one standalone Core `begin_support` transition converts the exact pending obligation immediately before preparation and starts the next support envelope. Receipt output enqueue/discard therefore completes before observation conversion, and the accepted Cost Profile Update only decides whether the distinct conditional continuation-formation obligation and its pre-reserved description set become pending or close. This keeps every owner-thread interval in exactly one Turn, support, or sequenced-event envelope.

Initialization returns exact Adapter, MLX, Backend Interface, complete Backend Capability descriptor, Backend Resource Signal Contract, and Backend Operation Bound Set identities plus both complete bounded descriptors, but makes no authorization or Resource Mode decision. Model Descriptor and Request Description generation are stateless: they create no resident model, opaque request handle, KV, or Sampling State. `describe_model` returns only a bounded raw canonical frame plus untrusted identity, hash, and vocabulary claims. The private Rust `model_descriptor` module parses that frame, independently derives its typed identity and hash, compares every claim and the Manifest's expected hash, and exposes only a field-private verified value; the Backend cannot authorize any descriptor field. The daemon-owned `request` input to `describe_request` contains the frozen Token Request, exact verified Model Descriptor, and current Backend Generation; the Result binds all three. The Backend performs no registry lookup and returns the complete finite Capability Requirement Set rather than a future batch/Shape choice, Envelope, applicable Certification Record, or exact authorized Key. Admission accepts only a current-generation Result, joins its requirements with fresh environment evidence, verifies the entire exact-key closure, freezes the Authorized Capability Set, and supplies certified bounds. A stale Result never reaches Admission or creates a terminal rejection: one Core description owner reissues resident Preparing requests in stable Request ID order under the original timeout, while Warming requests stay marked stale until their own load gate. Successful load advances Backend Generation, invalidates every older not-yet-admitted Request Description and the affected Revision's pre-load Model Descriptor observation. Before Candidate Formation or Admission, the daemon repeats `describe_model` over the registered Manifest, runs the same private verifier, requires exact registered verified frame/identity/hash/vocabulary equality, and sends its remaining Warming waiters plus every unrelated resident Preparing request through that same refresh owner; unrelated Warming requests remain stale until their own successful load, and loaded-Revision drift alone makes that Revision Unavailable. Request Materialization may begin only after Admission atomically commits its typed Resource Reservation and Timing Commitment. Its Result binds the Operation, Request, Resource Reservation, and Request Backend Allocation Budget and returns a checked complete allocated/never-allocated partition of that Budget; every complete or partial ownership outcome includes one opaque releasable identity. A terminal path proven never to have started materialization makes no Backend release call and Core withdraws its applicable unconsumed Reservation directly. A zero-ownership Materialization Result also makes no release call but authorizes Core to split the Request Backend Allocation Budget's proven never-allocated bytes from actual allocation entering Pending Reclaim; Backend results carry no output, transient-headroom, timing, or other daemon capacity authority. Any complete or partial Backend request ownership is consumed exactly once by Request State Release; the logical terminal retains the complete Request Backend Allocation Budget until its accepted synchronized Result binds and consumes that ownership and authorizes the checked Budget split. Missing identity, broken conservation, overflow, or inability to establish either required result is process-wide fail-stop, not assumed cleanup or retry.

Candidate Formation remains complete and policy-blind. Every Candidate returns one exact Capability Key and is rejected unless every member's frozen Authorized Capability Set contains it. `execute_turn` returns either a pre-execution Plan Rejection or, after execution starts and synchronizes, one Turn Receipt with bounded progress, staged output, and typed member outcomes. One Prefill invocation advances exactly one granted Prefill Chunk and returns its processed range plus continuation; it cannot retain control for the next schedulable chunk.

Only a Receipt already accepted by Core may be passed to `observe_turn_receipt`, which compares the prevalidated Receipt-bound expected profile/Backend Generation before mutation. Mismatch returns a typed rejection without mutation but proves existing divergence and therefore fail-stops before another Backend call. A match returns `unchanged` or atomically installs one Backend-owned profile and returns an `applied` Cost Profile Update binding Receipt, affected Model, and exact old/new versions. The Cost Profile Commit Barrier then requires that result to be the next Core Event; no other Core Transition or Backend call may intervene. Core mirrors only the profile identity, must commit it immediately, advance Backend Generation, invalidate every older Scheduling Snapshot, Turn Plan, and not-yet-admitted Request Description, route those accepted requests through the sole description-refresh owner, and mark only its affected Model dirty. A malformed result or failed Core commit after Backend mutation likewise triggers process-wide fail-stop, so the two sides never continue with divergent versions.

An Exclusive operation is callable only under explicit Core-authorized Exclusive Mode, Lease, resource bound, and certified Exclusive Safety Point. `transition_residency` has serialized load, unload, and bounded allocator/cache-reclaim variants. Successful load retains ownership and the complete Residency Reservation, then Core advances Backend Generation and performs post-load Model Descriptor equality and Request Description refresh while the Revision remains unavailable; terminal failed/cancelled load strongly rolls back to zero ownership and returns the trustworthy allocated/unallocated split. Unload requires zero request ownership and pending releases, then a successful Result returns the same split. Failed unload retains ownership and Reservation. Cache reclaim may preserve Model Residency, changes no ownership, and no transition result alone proves physical reclaim. `sample_backend_resources` returns only allocator/cache facts bound to the initialization Signal Contract; daemon-owned sampling and assembly produce complete Resource Evidence, from which the Resource Governor alone derives Resource Mode.

The Adapter implementation and source-facing Module Interface are C++. Rust crosses the private integration seam through a minimal C-compatible shim with opaque owned handles and coarse entry points corresponding to the operation family above. Inputs and results are bounded owned in-memory values; neither language retains references into the other's stack or object layout. C++ exceptions never cross the seam, and every native error becomes a trustworthy synchronized typed result or process-wide fail-stop according to its certified safety contract. There is no independent cancel-poll operation: external setters update one bounded Device Control Signal, and only its read-only view crosses into the active cancellable call. The shim raw deallocator has one checked empty-handle typestate and may run only after trustworthy initialization rollback or a successful Shutdown Result; the shell contains no Backend or MLX object, so this deallocator is nonthrowing, bounded, and carries no teardown authority. It rejects initialized or indeterminate live state without destruction. Adapter and MLX build, Backend Interface, Backend Bootstrap Manifest, complete Backend Capability descriptor, Backend Resource Signal Contract, and Backend Operation Bound Set identities bind every Certification Record; compatibility is checked at build and Backend Initialization rather than negotiated at runtime.

Backend Shutdown is invoked exactly once as the final owner-thread operation after Service Readiness is false, no Backend operation is in flight, and all request ownership and pending release are zero. It destroys remaining model, stream, cache, and root state and returns the handle to the empty typestate. Only its trustworthy synchronized success proving zero logical Backend ownership permits raw shell deallocation and the daemon's Clean Shutdown Boundary; process-local reservations remain charged until process exit and a successor's fresh baseline. Failure, an untrustworthy result, or a missed safe point fail-stops the process without retry, fabricated result, raw live-state destruction, or Clean Shutdown Boundary.

The Device Executor constructs and destroys all Adapter, MLX, stream, model, KV, and cache state on its owner thread. External threads can only enqueue coarse Runtime Events or set the bounded Device Control Signal; they cannot invoke the Backend Interface. The Event Loop admits owner-thread Effects only within the applicable Engine, Residency, Exclusive, or Support bound and never hides queued maintenance outside timing feasibility. The Operation Watchdog first sets cooperative cancellation and, if any certified next-safe-point bound is violated, terminates the whole daemon rather than detaching or restarting the owner thread. Restart performs ordinary Bootstrap with empty inference state. The MVP's coarse interface is the later architecture decision recorded by ADR 0018, which supersedes only the P-1C report's recommendation to defer every topology choice. P-1C itself remains RED: it supplies no relative-performance certification and establishes no permanent general FFI conclusion.

The Adapter Implementation organizes native state as logical per-Model Model Runtime capsules with explicit owner-affinity tokens, but maps every capsule to the same Device Executor thread in the MVP. The Backend Capability declares `max_overlapping_turns = 1`; neither the logical Seam nor individually certified Turns imply per-Model workers, a second MLX owner, or concurrent Metal execution. Any larger overlap value requires certification of the complete co-running set.

The Fake Execution Backend and C++/MLX Adapter must pass the same Backend Interface conformance fixtures for pre-call Bootstrap and initialization descriptor identity including the complete Backend Capability, contract-bound resource samples, current-generation Request Description and post-load Model Descriptor equality plus Request Description refresh, finite requirement and authorized-key membership, post-Admission ownership, no-call pre-materialization cancellation, exactly-once release and no early capacity reuse, terminal-release-before-unload ordering, Candidate completeness and typed exclusions, Cost Profile compare-and-commit including fail-stop after mutation, dirty-Model-only recomputation with global stale-Plan rejection, frozen Turn Plan membership, explicit Exclusive execution, successful load plus zero-allocation, partially allocated, or cancelled strong-rollback load outcomes, failed/successful unload and unchanged-ownership cache-reclaim transitions, every support lifecycle state, direct-call watchdog, complete daemon-envelope bound and sliding-horizon pool, read-only signals, owner affinity, one-Chunk Prefill continuation, exactly-once result-gated Backend Shutdown, trustworthy synchronized partial request outcomes, and fail-stop when no result can be trusted. The Fake remains a deterministic Core test Adapter and does not certify MLX correctness or performance.

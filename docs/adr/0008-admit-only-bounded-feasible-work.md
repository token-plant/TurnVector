# Admit Only Bounded, Feasible Work

Request Acceptance occurs after boundary validation, Ingress Budget reservation, and one-time Alias resolution, assigns a stable Request ID, and enters Preparing without claiming Admission. During Preparing the Execution Backend performs stateless validation over the daemon-owned frozen Token Request, exact validated Model Descriptor, and current Backend Generation. Its generation-bound Request Description returns the complete bounded Capability Requirement Set, Backend Capability declarations, ordinary Cost Profile estimates, and conservative resource/output/residency facts, but no future batch/Shape choice, Certification Envelope, applicable Certification Record, exact authorized Key, or authorization decision. Admission accepts only a current-generation description, matches every requirement against one fresh Environment Fingerprint and the exact-key Certification Authorization Index, requires at least one applicable Key per requirement, and freezes the complete finite Authorized Capability Set plus worst-case bounds in the Timing Commitment and Resource Reservation. A stale description never becomes an Admission rejection: the sole Core description owner keeps the request in Preparing or Warming and reissues bounded work in stable Request ID order under its original timeout. Any later Work Candidate carries one exact Key and is infeasible unless every member's frozen Set contains it. Preparation has its own operational timeout. A non-resident Revision enters Warming. Successful load advances Backend Generation and invalidates its pre-load Model Descriptor observation plus every older not-yet-admitted Request Description; while the Revision remains unavailable for Candidate Formation, the daemon repeats `describe_model` over the exact registered manifest, requires exact equality with the registered Model Descriptor identity and hash, and sends every bounded remaining waiter through that same refresh owner. Other resident Preparing requests invalidated by this load or a Cost Profile Update use the identical path. Drift marks the loaded Revision Unavailable and fails its waiters without Admission; generation change alone never fails an unrelated request. A resident Revision uses its already validated registered descriptor and obtains a current-generation Request Description directly. Only successful Admission atomically creates a typed capacity-ledger Resource Reservation and immutable Timing Commitment, after which Request Materialization creates private Backend state before Queued. Later Timing Profile changes apply only to new Admission. Preparing/Warming termination and Admission rejection release their pre-Admission budgets without a Backend call; after Admission, cancellation proven to precede materialization likewise makes no Backend release call and lets Core withdraw the complete unconsumed Resource Reservation. A zero-ownership Materialization Result also makes no release call but authorizes Core to release the Request Backend Allocation Budget's proven never-allocated remainder and move proven actual allocation into Pending Reclaim, while Core settles other unconsumed Resource Reservation components from its own facts. Once complete or partial Backend request ownership exists, a logical terminal retains the complete Request Backend Allocation Budget and requires exactly-once Request State Release; only its accepted synchronized result may authorize that Budget split. Activating a new Certification Record or changing a certified upper bound triggers Profile Revalidation; online estimate changes within fixed certified bounds do not alter the safety contract.

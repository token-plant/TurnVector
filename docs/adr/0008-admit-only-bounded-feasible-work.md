# Admit Only Bounded, Feasible Work

Every post-load Model Descriptor comparison in this decision, including abbreviated identity-and-hash wording below, runs the same private verifier over the complete raw frame and claims and requires exact equality with the registered sealed frame, Model Descriptor ID, typed Model Descriptor Hash, and nonzero vocabulary.

Request Acceptance occurs after boundary validation, Ingress Budget reservation, and one-time Alias resolution, assigns a stable Request ID, and enters Preparing without claiming Admission. During Preparing the Execution Backend performs stateless validation over the daemon-owned frozen Token Request, exact validated Model Descriptor, and current Backend Generation. Its generation-bound Request Description returns the complete bounded Capability Requirement Set, Backend Capability declarations, ordinary Cost Profile estimates, and conservative resource/output/residency facts, but no future batch/Shape choice, Certification Envelope, applicable Certification Record, exact authorized Key, or authorization decision. Admission accepts only a current-generation description, matches every requirement against one fresh Environment Fingerprint and the exact-key Certification Authorization Index, requires at least one applicable Key per requirement, and constructs the complete finite Authorized Capability Set plus exact Runtime Overhead Bound Set whose three-term Deadline Cost includes intrinsic work, support interference, and sequenced-event interference. A stale description never becomes an Admission rejection: the sole Core description owner keeps the request in Preparing or Warming and reissues bounded work in stable Request ID order under its original timeout. Any later Work Candidate carries one exact Key and is infeasible unless every member's frozen Set contains it. Preparation has its own operational timeout. A non-resident Revision enters Warming. Successful load advances Backend Generation and invalidates its pre-load Model Descriptor observation plus every older not-yet-admitted Request Description; while the Revision remains unavailable for Candidate Formation, the daemon repeats `describe_model` over the exact registered manifest, requires exact equality with the registered Model Descriptor identity and hash, and sends every bounded remaining waiter through that same refresh owner. Other resident Preparing requests invalidated by this load or a Cost Profile Update use the identical path. Drift marks the loaded Revision Unavailable and fails its waiters without Admission; generation change alone never fails an unrelated request. A resident Revision uses its already validated registered descriptor and obtains a current-generation Request Description directly. Only successful Admission uses one Core transition to atomically coordinate the sole Resource Capacity Ledger and sole Support Charge Ledger with request state: it commits the Authorized Capability Set, Bound Set, immutable Timing Commitment, actual initial-Materialization, initial-Candidate-Formation, and release Support Operation Obligations, reusable Future Turn Support Entitlement with its complete Support Outstanding Credit Vector, finite per-Turn and terminal membership-change operation requirements, and composite Resource Reservation together. Request Materialization then creates private Backend state before Queued; its accepted success only completes the initial-formation obligation's predecessor, and a later standalone `begin_support` after the materialization envelope ends starts Candidate Formation from its already conserved capacity. Later Timing Profile changes apply only to new Admission. Preparing/Warming termination and Admission rejection release their pre-Admission budgets without a Backend call; after Admission, cancellation proven to precede materialization likewise makes no Backend release call and lets Core atomically withdraw all unconsumed components, obligations, and entitlement claims from their owning ledgers. A zero-ownership Materialization Result also makes no release call but authorizes Core to release the Request Backend Allocation Budget's proven never-allocated remainder and move proven actual allocation into Pending Reclaim, while closing the now-impossible initial-formation and release paths and settling other components from Core facts. A partial-ownership Materialization failure is terminal: Core closes the now-impossible initial-Candidate-Formation obligation and Future Turn Support Entitlement, retains the distinct release obligation and complete Request Backend Allocation Budget, and requires exactly-once Request State Release. Any later logical terminal with complete Backend request ownership follows the same Budget-and-release rule; only the accepted synchronized release result may authorize that Budget split. Activating a new Certification Record or changing a certified upper bound triggers Profile Revalidation; online estimate changes within fixed certified bounds do not alter the safety contract.

The Future Turn Support Entitlement vector also reserves request-specific capacity for terminal cancellation-membership-change Candidate Formation. A cancellation that removes a request from an existing candidate invalidates that candidate and every not-started Plan containing it, then atomically rebinds, splits, merges, or closes their unstarted operation obligations and creates one shared terminal formation obligation for surviving members only when required. Only a later standalone Core `begin_support` transition after the cancellation envelope ends may convert that obligation and start `form_candidates`; the cancellation transition itself never overlaps the support envelope. Daemon output and transient-headroom capacity have equally explicit terminal owners: pre-materialization cancel withdraws them with every other unconsumed component, zero/partial Materialization failure withdraws them in the accepted Core transition, queued cancellation or Critical Eviction withdraws them after candidate invalidation, and an in-flight or ordinary terminal waits until Receipt output enqueue/discard has transferred or released concrete occupancy and no operation remains in flight. Backend Results authorize only their Request Backend Allocation Budget partition, never these daemon components.

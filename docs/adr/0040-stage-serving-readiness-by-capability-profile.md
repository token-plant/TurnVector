# Stage Serving Readiness by Capability Profile

P0 mutation readiness includes an exhaustive pre-owner check of the complete mutation token, exact Prepared Carry Reservation, current Support Ledger Generation, current next assignable Event Sequence, and full build-derived headroom. Every nonfatal mismatch or pre-owner preparation failure after carry creation atomically closes the unowned carry and resumes ordinary support without an Operation ID, Effect, or owner. A process cannot remain ready with an unowned carry or paused ordinary-support ledger.

TurnVector ships the first serving-ready implementation as the P0 Serving Profile: one authoritative Control Store, one immutable Runtime Identity Record-bound Storage Qualification Record, serialized durable Control Mutation, bounded non-recovery Audit, fail-closed schema handling, exclusive installation-wide process ownership through the Daemon Instance Lock, and restart with empty inference state. Identity Anchor, Runtime Identity Lease, Runtime Metadata authority, Runtime Bundle, Restore, Clone, same-ID Storage Qualification Rebind, multi-authority repair, Compatibility Custody, and the complete Bounded Integrity Lifecycle are unavailable and cannot gate or be advertised by this profile. Corruption or storage-binding drift that P0 cannot reconcile fails closed and requires creation of a new runtime under the same installation lock rather than partial repair, inferred recovery, or a new lock path.

P0 Service Readiness requires the OS-lifetime installation-scoped Daemon Instance Lock, exact equality between the session-frozen Storage Qualification Record and immutable Runtime Identity Record binding, exact Control Initialization or later mutation classification, a valid sole current Control State Generation, matching P0 Audit Sequence State, no Pending Audit Envelope, an Audit chain under the epoch-fixed Audit Registry Identity, a healthy session write guard, fail-closed schemas, an initialized Device Executor and compatible C++/MLX Adapter, the exact verified Daemon Core Build/Runtime Overhead Catalog/outer TurnVector Daemon Build tuple, one active Lifecycle Overhead Qualification matching the complete current Configuration Snapshot, stable platform facts, and every returned Backend descriptor, its active Owner-Thread Support Budget, Sequenced Event Interference Bound, and Stale Plan Disposition Bound, fresh Resource Evidence, and a serving operational state. A missing or drifted build/Catalog tuple, qualification witness, Configuration or returned descriptor identity, or active lifecycle descriptor remains non-ready and cannot make the first support call or admit a request. Whenever any predecessor process initialized the Backend, including graceful same-ID restart, Daemon Failure, or P0 Runtime ID replacement, the Process Reclaim Barrier requires predecessor exit proved by acquisition of that unchanged installation lock before the fresh resource baseline; a Clean Shutdown Boundary, Shutdown Result, new Runtime ID, new payload path, pre-lock sample, or pre-exit sample is invalid. True first genesis with no predecessor Backend initialization is explicit. When an initialized prior session reserved a suffix, readiness additionally requires its verified Clean Shutdown Boundary or a synchronized Crash Tail Boundary; fresh genesis has no prior tail. Bootstrap completes exact pending envelopes before tail handling. It never consults or creates a Locator, Anchor, Runtime Metadata row, Audit continuation pointer, repair source, implicit latest qualification, or second Control selector.

P0 initialization, range reservation, Control Mutation, pending clear, retention, and shutdown all share the same pre-writer Storage Barrier Failure latch. An actually attempted required durability barrier failure keeps Readiness false, stops Device work and all later writes, retains the Daemon Instance Lock until OS termination, and exposes authenticated read-only status without durability retry, failure marker or failure Audit record, or clean-release claim. Initialization uses `initialization_outcome_indeterminate` without a Control Mutation Operation ID or Token; later mutation uses Control Outcome Indeterminate only after its Operation ID exists. Before allocating a Control Mutation Operation ID, P0 must durably provide the complete build-derived Control Mutation Sequence Headroom outside Terminal Sequence Reserve; every ordinary assignment charges it, bounded Fence interleaving cannot consume its protected Result slots, and Audit Degraded retains it. When an Operation ID exists, required Fence file/parent synchronization, Store commit/parent synchronization, post-append Audit file/parent synchronization or verification, and clear commit/parent synchronization failures return Control Outcome Indeterminate, make no unchanged-state claim, and fabricate no Result. Individual Fence stale attempts remain internal; bounded exhaustion uses the sole Core publication-outcome transition to consume the Prepared Carry Reservation exactly once through one ordinary sequenced nonpublication failure Result, preserve predecessor Budget and charges, resume ordinary support, close the operation/headroom, and reopen the Runtime Closure Gate before typed busy. Graceful prepublication cancellation uses the same consumer. Committed Store success drives the Control-successor transition with the exact Prepared Carry Reservation, atomically activates the complete successor plus the exact same-or-replacement lifecycle descriptors named by the immutable daemon qualification witness over the unchanged Support Charge Ledger, advances Runtime Overhead Generation exactly once, advances the owner, and emits the dependent exact-envelope completion Effect; only that Effect's sequenced Result after pending clear lets Core release owner/headroom, reopen the Runtime Closure Gate, and return a typed completion disposition; daemon persistence orchestration immediately clears the Control Mutation Cancel Gate in the same Event Loop handling step with no intervening dequeue or Core transition and acknowledges success. Ordinary Audit append failure before its required synchronization attempt remains Audit Degraded and retains the same exact stage and Prepared Carry Reservation. Sequence Exhausted, Storage Capability Missing, and unreconcilable Control or Audit evidence are likewise non-ready; because P0 has no Bundle, Restore, Clone, same-ID qualification rebind, or same-ID repair capability, continued service requires a new runtime rather than an implicit profile upgrade.

A trustworthy exact-absent Store outcome closes the mutation through the sole Core publication-outcome transition and its pre-sequenced nonpublication failure Result, consumes the Prepared Carry Reservation, preserves predecessor Budget and charges, and resumes ordinary support, reopens the Runtime Closure Gate, and returns a typed terminal disposition without activation; daemon persistence orchestration immediately clears the Control Mutation Cancel Gate in the same Event Loop handling step with no intervening dequeue or Core transition; an indeterminate outcome retains the carry token and fabricates no Result. From mutation-owner creation through its terminal Result, P0 closes the Core-owned Runtime Closure Gate: every registered Core transition that would increase future sequence-and-Audit closure liability is rejected or deferred, while only nonincreasing progress over already charged obligations and read-only status that creates no Core object remain available. Those edges must close every accepted request, Turn Plan, Timing Commitment, Future Turn Support Entitlement, request Backend ownership, pending release, and output reservation before Commit Barrier entry, so Store/Audit I/O never pauses a live request obligation. Audit Degraded and the post-activation completion stage additionally reject discretionary Turn dispatch while preserving only bounded safety and closure work. Audit Safety Reserve prevents ordinary evidence from starving those records; when a mutation owner exists, their ordinary Event Sequences still debit its headroom and never borrow Terminal Sequence Reserve. Commit Barrier entry separately closes the exact Event Loop-owned Control Mutation Cancel Gate; Core never reads or mutates that gate. Every authorized Control Mutation cancellation then completes before Core conversion without Event Sequence, Audit, or headroom use: an exact tuple receives `cancel_window_closed`, any other tuple receives opaque `commit_in_progress`, and response write or connection termination releases its ordinary reservation.

Pre-ID range reservation is unsequenced daemon infrastructure with no mutation Operation ID or Audit Record. Its required commit or parent-barrier failure still latches Storage Barrier Failure and keeps Readiness false, but cannot return Control Outcome Indeterminate or claim the predecessor high-water; a successor classifies the possibly published sequence state.

The later Integrity Serving Profile may add those capabilities only with their already defined durability, evidence, qualification, and recovery contracts intact. Service Readiness is evaluated against the build-declared profile and reports that profile externally, so staged delivery narrows capability scope without weakening a claimed capability.

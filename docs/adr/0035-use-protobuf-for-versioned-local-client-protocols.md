Bootstrap status schemas bind Daemon Instance ID, a nonzero checked `uint64` Bootstrap Evaluation Generation, exact Condition Model and Action Decision Table identities, confirmed conditions, blocked checks, one Primary, and at most eight structurally possible Alternatives from one immutable evaluation and matched row. Each Daemon Instance begins at one and repeats only while canonical bytes for both artifact identities, sorted typed inputs, check outcomes, selected actions, and prerequisite states remain equal; observation time and diagnostic text are excluded. Any included change checked-increments generation, while before overflow the process emits no new status and exits and a replacement Instance restarts at one. `met` is evaluation-verified true, `unmet` safely false but externally satisfiable, and `blocked` names one preventing check. Unmet and blocked routes remain visible; proved-impossible routes do not. Every alternative has one distinct action ID and sorted unique conjunctive prerequisite list; commands revalidate and never accept generation as authority. Duplicate IDs, zero, OR, NOT, nesting, Primary repetition, absent/extra blockers, and non-canonical order are Protocol Violations. Older clients preserve and display unknown future IDs without evaluating them.

The canonical Initialization Manifest schema generates `initialization_manifest_binary_max_bytes`, and CI proves it with a worst-case fixture. Control Hello and status expose process-fixed `initialization_manifest_repair_effective_max_bytes`; it constrains only incoming repair. Oversize returns non-retryable `manifest_repair_limit_exceeded` before allocation or Hashing. Only a selected Control minor defining the variant and an effective set containing the distinct registered `manifest_repair_limit_detail_v1` capability authorize `ManifestRepairLimitDetail`, whose exact three `uint64` fields are `request_bytes`, `effective_max_bytes`, and `binary_max_bytes`; it contains no bytes, Hash, path, or source. An older minor or peer without that capability receives the same reason without detail. The reason means Policy replacement plus restart, grants no exemption, and creates no durable condition or Decision Table input.

The Pre-Locator Prune Failure Reason registry fixes IDs 1-7 as `identity_changed`, `type_changed`, `parent_unavailable`, `directory_not_empty`, `permission_denied`, `io_failure`, and `multiple_links`, with zero invalid. Generated handling selects the first definitive invariant in parent, type, identity, regular-file link-count, directory, permission, then other-I/O order: absent or replaced expected parent maps to 3, present wrong-type target to 2, expected type with different identity to 1, regular target with `st_nlink != 1` to 7 without unlink, post-child `ENOTEMPTY` to 4, any `EACCES` or `EPERM` to 5, and every remaining OS failure to 6. Link count is a prune safety prerequisite rather than object identity; `multiple_links` has no force/skip variant, and after restoring `st_nlink == 1` rerun revalidates parent, type, identity, File Hash, and link count for all targets from the beginning, while wire syscall position, `errno`, and text are diagnostics only.

The Data Plane and Control Plane use variable-length Protobuf payloads behind a four-byte unsigned big-endian length prefix rather than native layouts or a hand-built binary codec. Declared length is checked before allocation. Each family owns schema, major/minor versions, and one append-only `uint32` capability registry, while sharing canonical identifiers and Structured Error fields. Structured Error has a bounded optional typed-detail `oneof`; each detail variant owns a distinct versioned Protocol Capability ID rather than a generic detail capability, and a sender may populate it only when the selected minor defines that exact variant and the effective set contains that ID. Otherwise it sends common code/reason fields alone. Unknown or unsolicited detail is a Protocol Violation, never text fallback. Registries reserve zero and never reuse meanings; generated DTOs stay outside Runtime Core. Schemas use explicit presence, reserve deleted fields, and classify ignorable additions as minor while semantics need capability or major. Runtime, History Epoch, and Operation IDs encode exactly 16 bytes and render as 32 lowercase hex, not UUID text.

A plane-specific Hello carries family, one major, bounded strictly increasing minor entries binding each number to canonical descriptor SHA256 plus sorted unique numeric `provided` and `required_peer` capability IDs, directional typed limits, build identity, and embedded Protocol Support Manifest hash. Duplicate, unsorted, or zero IDs are Protocol Violations. Unknown provided IDs are ignored, unknown required-peer IDs reject negotiation, and each known required set must fit the peer. Named quantities retain `offered_max`, `required_min`, or `exact` semantics. The response selects the highest common non-revoked candidate and returns known capability intersection plus effective limits and Daemon Instance ID. Data and Control responses freeze write durations under binary maxima. Control also reports immutable `model_registry_limit`; registration, Restore, and Clone enforce it before successor or `PREPARED` state, counting all registered Revision lifecycle states and excluding Aliases. Maintenance Capability is a registered Control capability, but it is effective only on an authenticated Control connection whose peer credentials also match the Installation Policy's distinct live-maintenance allowlist; negotiation alone is insufficient. It expires on disconnect or Daemon Instance ID change, and a new connection must negotiate again without canceling any already durable operation. Offline maintenance has no protocol capability and uses separate Installation Policy authorization before locks. Unequal major, descriptor mismatch, unsatisfied requirements, inadequate limits, exact mismatch, or no usable entry receives one stable bounded incompatibility response. Build and whole-manifest hashes are diagnostic; selected descriptor hash equality is mandatory.

Public connections permit only negotiated bounds on pipelined command count and bytes. Each command has a client-assigned nonzero strictly increasing unsigned 64-bit connection-local Command ID checked with one high-water mark; every structurally valid command consumes its ID even if rejected, and an explicit retry uses the next ID. The value never wraps. After structural validation and before Event Loop admission, each command reserves a slot and maximum encoded bytes for its Direct Response and remains charged until the complete frame is written or the connection terminates; enqueue converts reservation to actual frame occupancy. A separate single fixed rejection reservation handles lack of ordinary response capacity; if neither can be reserved, the connection closes, and Output cannot consume either reserve.

Exactly one Direct Response echoes the ID for each legal command while the connection remains live; request state, output, and terminal status are separate asynchronous events, and nothing is replayed after disconnect. Command ID is not idempotency. Commands enter the Event Loop in receive order, while responses may complete out of order; the single writer places each Direct Response before causally produced Status or Output. Write failure leaves delivery unknown, and frozen deadlines close stalled connections without replay. A published Control Mutation whose strong Audit barrier fails uses the stable `outcome_indeterminate` response variant with daemon Operation ID and current Control Mutation Token; clients must inspect that token or resume by operation and cannot interpret the response as rejection. Only a connection currently holding Maintenance Capability may introduce a trusted-tool-generated Operation ID, and the daemon rejects any collision visible in active staging or bounded tombstones; other supplied IDs can only resume an exact match. The tool, not the bounded protocol state, owns the global non-reuse obligation after tombstone eviction. Cancellation Accepted follows its Core Event, `u64::MAX` closes ingress, protocol violations close after at most one bounded error, and Domain Rejections preserve the connection.

The repository stores source `.proto` files, each canonical family-major capability registry including reserved removed IDs, pinned generation-tool identities, canonical descriptor hashes, cross-language golden fixtures, and one build-generated embedded Protocol Support Manifest per protocol-family build. It separately stores canonical append-only `u32` Bootstrap Condition, Blocked Check, Required Action, Recovery Prerequisite, and Metadata Role registry files. Each namespace reserves zero, never reuses a published ID, retains removed meanings as reserved, and is the sole source for distinct strongly typed Rust/C++ and protocol constants; Protobuf enum declaration order and IDs from another registry never assign domain identity. Each Metadata Role entry additionally binds one literal basename, persistent or volatile classification, inclusion in identity hashing, evidence-copy requirements, and permitted repair treatment. The MVP registry contains exactly the Runtime Metadata main database as persistent identity and its DELETE-mode rollback journal as volatile evidence when present; WAL and SHM basenames are unrecognized. Runtime configuration, plugins, filesystem discovery, and SQLite naming heuristics cannot allocate or reinterpret a role. The generated Rust recognizer accepts only the registered basename and required regular-file type; any other object is an Unrecognized Metadata Role. Each registry's fixed canonical bytes have a SHA-256 recorded in the build manifest and exposed only as build provenance and diagnostics. Registry-hash equality is not a wire compatibility gate: status encodes registry identities as `uint32` fields, not Protobuf enums, alongside bounded typed details, so an older client may preserve or display an unknown added ID without guessing its meaning. CI rejects ID or basename duplication, reuse, changed classification or semantics, cross-namespace type substitution, non-canonical bytes, hash or generated-constant drift, or a decision-table rule referencing an absent Required Action or Recovery Prerequisite registry ID. It also exercises closed-main, present-journal, hot-journal, unknown-WAL, unknown-SHM, and unknown-object manifests and proves that a binary lacking an observed role reports both Metadata Repair Required and Migration No Path, while a compatible binary can enter only that role's registered repair path. The protocol manifest's capability subsets and generated language constants derive only from the capability registry; hand-edited generated output never allocates any ID. Generated Rust and C++ sources remain ignored build products, and CI proves deterministic regeneration. For each minor, the canonical hash input is a deterministic `FileDescriptorSet` containing the root schemas and all transitive imports, with source information removed, files sorted by canonical name, and deterministic binary encoding; `.proto` text and generated Rust or C++ code are never hash inputs. The manifest binds every supported or revoked minor to that SHA256, sorted unique provided and required-peer registry subsets, directional typed-limit metadata, and stable reason metadata. It bounds Hello entries and contributes its whole hash to diagnostics and Audit. Neither Control State, runtime flags, nor a mutable sidecar can alter it; build verification and startup fail if registry, embedded manifest, generated descriptors, and fixtures disagree. The bounded sorted-entry negotiation permits revoked holes rather than pretending support is one continuous range.

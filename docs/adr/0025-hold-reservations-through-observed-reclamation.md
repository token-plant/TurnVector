# Hold Reservations Through Observed Reclamation

Admission creates one typed composite request Resource Reservation through a single Core transition rather than physically allocating maximum KV or output buffers. The sole Resource Capacity Ledger owns its Request Backend Allocation Budget, aggregate output, and transient-headroom components; the separate Support Charge Ledger owns initial progress/release Support Operation Obligations and the Future Turn Support Entitlement with its complete Support Outstanding Credit Vector; Timing Commitment and evidence remain request-owned Core state. Both ledger generations are revalidated and both sides commit or roll back atomically, with no component duplicated. The Request Backend Allocation Budget is the only component that crosses the Backend Interface. Separately, every model load requires a Governor-owned Residency Reservation derived from its Model Descriptor for shared weights and runtime residency cost; this cost never belongs to the first Warming request. Actual allocations consume the applicable reserved budget, and unused committed capacity cannot be admitted elsewhere while active. Each output-producing Turn also reserves its maximum visible output slots. A request path proven never materialized has no Backend ownership and makes no release call; Core may withdraw each unconsumed Reservation component from its owning ledger. A zero-ownership Materialization Result likewise makes no release call but authorizes Core to release the Request Backend Allocation Budget's proven never-allocated remainder and move proven actual allocation into Pending Reclaim. Once complete ownership exists, request termination only orders exactly-once owner-thread Request State Release and releases no Backend allocation capacity itself. A partial-ownership Materialization failure additionally closes the now-impossible initial-Candidate-Formation obligation and Future Turn Support Entitlement while retaining its distinct release obligation and complete Backend Allocation Budget until that release Result. Model unload cannot start until accepted Release Results have consumed all request ownership for that Model. Only an accepted synchronized zero-ownership Materialization Result, ownership-consuming Request Release Result, zero-ownership failed/cancelled-load Residency Result, or successful-unload Residency Result may authorize its applicable checked complete Request Backend Allocation Budget or Residency Reservation allocation split; a successful load retains the complete Residency Reservation and a failed unload retains ownership and charge. Pending Reclaim remains charged until Adapter allocator evidence plus daemon process-footprint convergence proves reclamation. After Daemon Failure, the next process inherits no live ledger and remains behind a Process Reclaim Barrier until exclusive lifetime locks prove the old process is gone and fresh system Resource Evidence establishes a baseline after OS reclamation. A Reclaim Stall during a live daemon triggers a bounded allocator/cache-reclaim Residency Transition and deterministic idle-Model reclamation plus Guarded Mode, then follows normal Resource Mode escalation without ever treating a cache result or sample as proof of free capacity.

Aggregate output and transient-headroom capacity never follows the Backend Budget result path. Core withdraws it atomically on a pre-materialization cancellation, zero/partial Materialization failure, or queued cancellation/Critical Eviction after candidate invalidation. An in-flight cancellation or ordinary terminal retains it until the accepted Receipt and directly resulting Output Publication enqueue/discard have transferred or released every concrete output occupancy and no in-flight operation remains. Only then does the sole Resource Capacity Ledger release those daemon components; Request State Release still governs only Backend ownership and the exact Backend Budget partition.

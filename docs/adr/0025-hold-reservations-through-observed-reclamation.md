# Hold Reservations Through Observed Reclamation

Admission creates a typed request Resource Reservation in a capacity ledger rather than physically allocating maximum KV or output buffers. Its Request Backend Allocation Budget is the only component that crosses the Backend Interface; aggregate output, transient-headroom, and timing components remain daemon-owned and settle through their own Core, in-flight-operation, and publication rules. Separately, every model load requires a Governor-owned Residency Reservation derived from its Model Descriptor for shared weights and runtime residency cost; this cost never belongs to the first Warming request. Actual allocations consume the applicable reserved budget, and unused committed capacity cannot be admitted elsewhere while active. Each output-producing Turn also reserves its maximum visible output slots. A request path proven never materialized has no Backend ownership and makes no release call; Core may withdraw its applicable unconsumed Reservation directly. A zero-ownership Materialization Result likewise makes no release call but authorizes Core to release the Request Backend Allocation Budget's proven never-allocated remainder and move proven actual allocation into Pending Reclaim. Once ownership exists, request termination only orders exactly-once owner-thread Request State Release and releases no Backend allocation capacity itself. Model unload cannot start until accepted Release Results have consumed all request ownership for that Model. Only an accepted synchronized zero-ownership Materialization Result, ownership-consuming Request Release Result, zero-ownership failed/cancelled-load Residency Result, or successful-unload Residency Result may authorize its applicable checked complete Request Backend Allocation Budget or Residency Reservation allocation split; a successful load retains the complete Residency Reservation and a failed unload retains ownership and charge. Pending Reclaim remains charged until Adapter allocator evidence plus daemon process-footprint convergence proves reclamation. After Daemon Failure, the next process inherits no live capacity ledger and remains behind a Process Reclaim Barrier until exclusive lifetime locks prove the old process is gone and fresh system Resource Evidence establishes a baseline after OS reclamation. A Reclaim Stall during a live daemon triggers a bounded allocator/cache-reclaim Residency Transition and deterministic idle-Model reclamation plus Guarded Mode, then follows normal Resource Mode escalation without ever treating a cache result or sample as proof of free capacity.

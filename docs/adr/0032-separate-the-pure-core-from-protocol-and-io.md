# Separate the Pure Core from Protocol and I/O

The Rust workspace uses three primary crates: a serialization-independent `core` crate, a `protocol` crate for bounded wire DTOs and validated Domain Type conversion, and a `daemon` crate for the Runtime Event Loop, process supervision, persistence, sockets, timers, and other I/O. The C++ Backend Worker remains a separate native component. The Runtime Core synchronously handles one strictly sequenced Core Event and stages successor state or a controlled delta, ordered outcomes, and explicit Effects. It commits only after production Core Invariants pass, preserving prior state and emitting no Effect on failure; this atomicity contract does not require whole-state cloning. Legal conflicts are Domain Rejections, while sequence or invariant failure is a global Core Fault. Effects are data with Operation IDs, relevant generations, stable order, and explicit dependencies; daemon executors return completion, failure, cancellation, or indeterminate Effect Results as later Core Events, and duplicate or unknown results never reapply state. IDs, units, instants, durations, bytes, and sequences use distinct newtypes. Generated protocol structures and serialization dependencies do not enter the Core. Only a small daemon boundary exposes ports such as Backend transport, Control State storage, Audit sink, Resource sampler, and timer; Core modules are not individually trait-wrapped. Implementation proceeds from Core invariants, explicit test time, Fake Backend, and deterministic replay to protocol and daemon integration, then to the C++/MLX Worker.

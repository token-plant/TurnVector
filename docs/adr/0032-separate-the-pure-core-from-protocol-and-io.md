# Separate the Pure Core from Protocol and I/O

The Rust workspace uses three primary crates: a serialization-independent `core` crate, a `protocol` crate for bounded public wire DTOs and validated Domain Type conversion, and a `daemon` crate for the Runtime Event Loop, persistence, sockets, timers, and other I/O. A statically linked C++/MLX Adapter is an internal native module in the same process. The Runtime Core synchronously handles one strictly sequenced Core Event and stages successor state or a controlled delta, ordered outcomes, and explicit Effects. It commits only after production Core Invariants pass, preserving prior state and emitting no Effect on failure; this atomicity contract does not require whole-state cloning. Legal conflicts are Domain Rejections, while sequence or invariant failure is a global Core Fault. Effects are data with Operation IDs, relevant generations, stable order, and explicit dependencies. The Runtime Event Loop executes Backend Effects by direct calls on its Device Executor thread and returns their typed in-memory results before another Turn; bounded executors return non-Backend I/O results as later Core Events, and duplicate or unknown results never reapply state. IDs, units, instants, durations, bytes, and sequences use distinct newtypes. Generated protocol structures and serialization dependencies do not enter the Core or Backend Interface. Only a small daemon seam exposes interfaces such as the Execution Backend, Control State storage, Audit sink, Resource sampler, and timer; Core modules are not individually trait-wrapped. Implementation proceeds in seven gated phases: pure Runtime Core and deterministic replay; Fake Execution Backend, Device Executor, and Runtime Event Loop; Resource Governor, Reservations, Residency, and Pending Reclaim; in-process C++/MLX Adapter; Data and Control Plane sockets, Protobuf, and output backpressure; SQLite Control Store, bounded P0 Audit, and Daemon Instance Lock; and TurnVectorBenchmark qualification.

Inside the `core` crate, Request Lifecycle, Scheduling and Arbitration, Resource Policy, and Operation Ledger are private pure Modules coordinated by one atomic Transition Coordinator. They do not become actors, processes, public traits, or independent commit owners. This preserves one deep external Core Interface while concentrating local state, invariants, and tests in the Module that owns each rule.

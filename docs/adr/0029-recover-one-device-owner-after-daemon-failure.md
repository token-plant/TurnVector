# Recover One Device Owner After Daemon Failure

In this ADR, the device owner is the one TurnVector daemon together with its in-process Device Executor; there is no distinct MLX process or device lease. Logical Fresh Root Boundary and Physical Installation Ownership Boundary are deliberately separate. Logical requalification may replace semantic, Schema, Tool and dependency trust but never proves that the prior serving process is gone or releases a resource charge. A new Installation requires independently agreed serving-process lifetime, Daemon Instance Lock and Runtime Identity Lease generations, and fresh resource observations, regardless of new credentials, root identities, PID absence, or operator intent.

Independent OS and Device Ownership Proof disagreement advances only through one finite, one-active, two-Job chain while the service remains nonready and every Reservation and Pending Reclaim remains charged. Exhaustion is an Installation ownership boundary: neither a newer process, PID absence, epoch, timeout nor lineage preference authorizes takeover; only a wholly new independently qualified Installation and ownership authority root importing all conflict evidence may continue after fresh OS/device state is proved.

Conflicting old- and new-lineage ownership evidence creates a Cross-Lineage Conflict Incident: age, epoch, timeout, operator preference, PID absence, process exit and either lineage alone select no winner. The service remains nonready and all Reservations and Pending Reclaim remain charged until two fresh Jobs byte-agree on an Independent OS and Device Ownership Proof binding the serving-process lifetime, both existing lifecycle-lock generations, the in-process Device Executor state, and fresh resource observations. Proof disagreement preserves the Incident and charges rather than enabling takeover.

Conflicting ownership-release evidence advances only through one bounded two-Job repair chain while the service remains nonready and every Reservation and Pending Reclaim stays charged. Exhaustion permits no timeout or new epoch under the old authority; continuation requires a wholly new independently qualified ownership authority lineage that imports the full terminal and proves release with fresh Resource Evidence.

Certified process exit does not establish reclaimable capacity by itself. If lifecycle-lock release and the fresh resource baseline cannot be proved, Bootstrap keeps the service nonready, retains Reservation and Pending Reclaim, and permits only authority-owned repair followed by fresh Resource Evidence; timeout, a new epoch, manual clearing, or a concurrent replacement daemon is forbidden.

Authenticated status binds Daemon Instance ID, a nonzero checked `u64` Bootstrap Evaluation Generation, exact Condition Model and Action Decision Table identities, and at most eight structurally possible Alternative Recovery Actions from the same immutable evaluation and row as its one Primary Required Action. Each Daemon Instance starts generation one and repeats it only while canonical bytes for both artifact identities, sorted typed inputs, check outcomes, selected actions, and prerequisite states remain equal; observation time and diagnostic text are excluded. Any included change checked-increments generation, while before overflow the process publishes no new status and exits and the replacement Instance begins at one. Each action ID appears once with sorted unique Recovery Prerequisites: `met` is evaluation-verified true, `unmet` is verified false but externally satisfiable, and `blocked` names the one check that prevented verification. Proved-impossible routes are omitted, every command revalidates rather than treating generation as authority, and OR, NOT, nesting, duplicates, Primary repetition, and untyped prose are forbidden.

Before Qualification Lineage Reset creates its permanent record, the tool computes `max(67_108_864, policy_required_bytes)` with checked absolute `u64` arithmetic; percentage or relative inputs are invalid. Changing that binary floor or its algorithm changes Storage Capability Profile identity and requires offline requalification plus explicit Storage Qualification Rebind, while a Policy-only increase changes only the operation's bound effective evidence. Exact generated remaining-write bytes are added separately. The tool opens the exact volume root and accepts only a Profile-qualified volume that reports persistent and 64-bit object IDs. Checked nonnegative descriptor-relative `f_bavail * f_bsize` must cover the total before staging and, after Record and candidate Head synchronization, immediately before publication. Failure leaves the old Head unchanged and candidates orphaned. The Record binds effective margin, both observations, Policy Identity, and Profile; no logical record-count limit exists.

Initialization Manifest Repair is selected before an independently required Control repair or Control-schema migration. It validates bound, computed File Hash, exact Locator equality, strict canonical decoding, and embedded identity before evidence copy or `PREPARED`; after success the daemon exits and a fresh Bootstrap must verify the Manifest before any Control action begins.

When a pending Rebind cannot validate exact custody, Bootstrap reports Rebind Tool Custody Restoration as Primary Required Action without changing the token or any Runtime byte. The separately authorized offline restoration synchronizes only exact digest-matching custody bytes and returns non-authoritative command evidence; it writes no Runtime Receipt or Audit Record. If exact bytes remain unavailable, same-ID Rebind stays pending and status identifies qualifying new-ID Clone from a preexisting valid Runtime Bundle as an Alternative Recovery Action with exact prerequisites.

Qualification Lineage Reset Records are permanent installation provenance whether selected by a Head or orphaned by failure, supersession, or a fresh reset. No cleanup, TTL, retention bound, or later successful qualification removes them.

A daemon with Initialization Provenance Missing may execute only one exact prerequisite repair when Manifest repair is not yet viable: Metadata repair requires independently valid Control and Audit, and Audit/Audit Pointer repair requires independently valid Control and Metadata. It then exits so the next Bootstrap rederives every condition before Manifest repair. Metadata and Audit damage together is Cross-Authority Damage and admits only registered-Bundle Clone. Manifest absence takes precedence over a simultaneously degraded Locator; Manifest repair, daemon exit, and fresh Bootstrap precede Locator Repair.

If token-selected Rebind Tool Custody is unavailable after `PREPARED`, Bootstrap leaves the same token pending and writes nothing. A freshly authorized offline invocation may reinstall, synchronize, and revalidate only exact whole-bundle-digest-matching bytes on the candidate-qualified Identity-root volume, then resume with that exact executable. It cannot rewrite or clear the token, substitute another build, or reconstruct the tool. Without exact bytes, same-ID recovery remains pending and only a new-ID Clone from a preexisting valid Runtime Bundle is available.

Qualification Lineage Reset resumes only by an explicitly supplied Reset Record File Hash; no Head or record-directory scan chooses it. After reauthorization and complete record verification, an exact candidate Head completes, an exact old Head republishes the same candidate and barriers, and any third Head fails. Omitting the hash starts a distinct reset with a new lineage and record, leaving all earlier unselected records orphaned.

During service, a Daemon Instance Lock in the stable runtime container admits one daemon or offline operator for that container while allowing only its `current/` payload to be replaced. After that lock and before opening Control, initialized startup validates one fixed non-symlink regular-file Runtime Locator Record containing two independent fixed-size, versioned, CRC-protected slots. Each slot binds the same 16-byte Runtime ID, exact Initialization Manifest File Hash, and creation-time qualification generations. Two valid slots must agree completely; one valid slot still establishes its ID but confirms Locator Degraded, no valid slot in an identity-bearing container is Locator Unrecoverable, and two valid unequal slots are Identity Conflict. The Locator grants no authority: the daemon uses its one established ID to acquire the host lease and then requires exact agreement among Locator, selected Anchor, Runtime Identity Record, current Generation, Metadata, and Audit. No runtime-directory name, command-line value, identity-root enumeration, or candidate Control row can replace, choose, or recreate it. The Locator-selected Manifest remains permanently at its canonical File Hash path in a dedicated stable directory, is verified on every Bootstrap, and is never rewritten on upgrade. Missing or corrupt exact Manifest bytes in an established Runtime confirm Initialization Provenance Missing without changing the Locator-established ID or suppressing other safely obtainable checks. An offline operator may attempt the container lock only after Offline Maintenance Authorization has verified one fixed Installation Policy snapshot and its effective UID or one kernel process group against the offline-maintenance allowlist; root and directory access are not authority. A separate Runtime Metadata Store retains bounded maintenance and publication state outside the replaceable payload. A separate installation-fixed absolute identity root is outside every runtime, owned by the fixed service UID and GID, not runtime-configurable, and contains immutable Storage Qualification Records plus one fixed two-slot Head per filesystem UUID and Storage Capability Profile but no central database. Each Head payload binds the random current Storage Qualification Lineage ID and that lineage's checked generation. For each Runtime ID the root contains a host-scoped Runtime Identity Lease and a persistent two-slot Identity Anchor. Each fixed-capacity format-neutral slot envelope records format major, bounded payload length, `u128` Anchor Slot Generation, payload bytes, and an envelope CRC. The versioned payload records exact currently authorized Runtime and Identity-root qualification records, History Epoch ID, Generation Hash, current typed Audit Continuation Hash, last synchronized Audit Head Hash and Event Sequence, durable reservation high-water, Anchor Ownership with a separate `u128` Daemon Session Generation, optional registered Recovery Bundle Hash, optional unresolved Metadata Role Block identity, and at most one fixed-size Publication Token. Both counters use checked successor arithmetic and never wrap. Readers select the highest envelope-valid generation before parsing its major; unsupported major is Migration No Path and never authorizes a lower-generation fallback.

The daemon holds the lease for its lifetime and proceeds only when its full identity, generation, current Audit Continuation Hash, and Audit Head Hash match the Anchor. Every established Runtime independently requires the Locator-selected Manifest bytes to match their exact File Hash for Service Readiness; a failure remains Initialization Provenance Missing rather than Locator Unrecoverable or evidence that another Manifest may be chosen. When Locator, established Anchor, and current qualification otherwise agree, that condition still permits `CLAIMED`, required rollback recovery, independent Control and Metadata inspection, and a narrowly authorized live-repair executor, but no Device Executor, service, ordinary Control mutation, or unrelated maintenance intent. Initialization Manifest Repair accepts only externally supplied bytes whose exact File Hash equals the established Locator value, preserves a typed missing-file observation or the complete corrupt original as immutable Repair Evidence, and binds that evidence, candidate, Receipt, and Pending Audit Envelope in Anchor `PREPARED`. A missing canonical object is published create-if-absent; a corrupt one is replaced by atomic same-volume exchange that retains the displaced bytes; both paths synchronize the parent before Anchor `COMMITTED`, exact standalone Receipt and Audit synchronization, pending clear, and `COMPLETED`. Native inspection permits only the bound predecessor observation or bytes and exact candidate, so the operation cannot choose content or change Locator, Runtime ID, Manifest Hash, or creation provenance. After Locator publication but before first initialization completion, a missing Anchor is legal only when that immutable Manifest and every named candidate verify; the Manifest alone authorizes creation of the first `PREPARED` Anchor and deterministic forward completion. Otherwise, if both Anchor slots are absent or invalid, Bootstrap reports Anchor Unrecoverable: same-ID Restore and repair are forbidden, and only an operator-supplied verified Bundle may Clone to a new identity because neither Bundle nor Control State can reconstruct the old host identity or its lost Recovery Bundle Registration. Registration stores only Bundle Hash and lineage proof, never its path or bytes, and external Bundle availability is not ordinary Readiness. An occupied lease may be retried with bounded jitter, but a mismatch against a valid selected Anchor is persistent Identity Conflict with Service Liveness and authenticated status only; no Device Executor, Control Repair, force takeover, or Anchor deletion is offered. Restore acquires the preserved ID and proves Bundle lineage; Clone generates and leases a new ID before its first Anchor. Neither lock is inferred from PID, socket, or path.

Before Runtime creation or Clone, an offline qualifier holds the installation qualification lock and performs the Profile's real syscall probes in isolated scratch directories on the proposed Runtime Authority Volume and Identity-root volume. For each exact filesystem UUID and Profile, a fixed two-slot Storage Qualification Head binds one random Lineage ID; two valid slots are generation-compared only when that ID agrees, and the highest valid checked lineage-scoped generation supplies the append predecessor. One valid slot permits the next ordinary successor append and thereby restores redundancy; different valid Lineage IDs, no valid slot, equal-generation disagreement, or a broken selected predecessor chain blocks ordinary qualification. The immutable successor record binds that Lineage ID and predecessor and is fully synchronized before the Head advances, while a synchronized record left unselected by a crash is orphan staging that directory scan, later qualification, Head recovery, and Bootstrap never adopt automatically. When no valid Head slot, different valid Lineage IDs, or equal-generation disagreement prevents lineage selection, an explicit offline Qualification Lineage Reset under the same qualification lock atomically publishes two equal `NO_PREDECESSOR` slots carrying a new random Lineage ID at the fixed Head path. The reset retains all earlier and orphan records and every Runtime's exact bound references, scans for and adopts no record, and leaves the first successor unavailable until a later qualification completes the Profile's real probes. Each immutable generation also binds the exact 16-byte filesystem UUID obtained with `getattrlist(ATTR_VOL_UUID)` on an opened volume root, exact OS build, TurnVector build, Profile identity, its build-owned `EINTR` completion deadline, complete probe results, record format, and lineage-scoped predecessor; history is retained. A path, mount point, volume name, device node, or session-local `fsid` never substitutes for that persistent identity, while descriptor-relative `statfs` comparisons prove current same-filesystem relationships. The same Profile identity and deadline govern Runtime barriers, and Installation Policy cannot override either. The Initialization Manifest retains exact creation records, while every established Anchor binds only the current records. Any OS build, TurnVector build, Profile, or filesystem-UUID change requires offline requalification followed by explicit Storage Qualification Rebind under current-Policy authorization, both locks, and the selected Anchor before startup. Before `PREPARED`, the candidate TurnVector build places a self-contained exact tool bundle in installation recovery custody outside every Runtime, and the Publication Token binds that bundle's content digest rather than its path. It cannot be deleted before Rebind `COMPLETED`; afterward only explicit cleanup may remove it. That exact offline executable is the sole Rebind executor and resumer; it must understand the selected predecessor formats, treats predecessor qualification records only as proof of the current binding, and uses candidate records to govern every write barrier and resulting byte. Before `PREPARED`, failure changes no Runtime authority. After `PREPARED`, a crash or barrier failure preserves the fixed token, returns `outcome_indeterminate` when possible, performs no cleanup or later write, and exits; only an explicit invocation of that same candidate-build tool may inspect exact predecessor/candidate state and continue the intent. Daemon Bootstrap reports the pending Rebind, writes no `CLAIMED`, and never reconciles it. A completing tool stores both record sets in its Publication Token, advances only the Anchor through `PREPARED` then `COMMITTED`, strongly synchronizes its standalone Receipt and Audit, clears pending evidence, and preserves Runtime ID, Locator, Manifest, and Control meaning. Otherwise Bootstrap performs no write probe or latest-generation search: after Locator validation and Lease acquisition it read-only checks the Anchor-selected current records, current volume identities and relationships, build bindings, and either the complete established Anchor or the selected pending Manifest. A missing, stale, foreign, or invalid current record is Storage Capability Missing and stops before `CLAIMED` while retaining both locks. With an established Anchor and all applicable claim checks valid, the daemon writes `CLAIMED` with a checked successor session generation binding its predecessor before its first SQLite open, any hot-journal rollback, any other recovery mutation, or Device Executor startup. It recovers Control before Metadata and retains independent results; a logical Control failure does not suppress Metadata inspection. Each SQLite write transaction retains `journal_mode=DELETE`, `synchronous=FULL`, and `fullfsync=ON`, and successful commit is followed by explicit synchronization of that database's parent directory before any Anchor or other external authority may advance. Cross-object publication also synchronizes non-SQLite candidates with `F_FULLFSYNC` and every affected parent directory after the native namespace operation; it writes Anchor `PREPARED`, invokes the authority kind's exact native durability point, and writes Anchor `COMMITTED` before strongly synchronized Audit and acknowledgement. One required durability syscall interrupted by `EINTR` may restart only that same call on the same open descriptor without semantic state advancement until the Profile-bound monotonic deadline; deadline exhaustion or any other error confirms Storage Barrier Failure rather than an operation retry or capability downgrade. The daemon immediately requests Device Executor Shutdown and stops every further Runtime write, blocks any later check that could require a write, retains both locks with Service Liveness and authenticated read-only status until OS signal, and retains a structured in-memory Barrier Failure Observation with session, optional Operation ID, authority kind, phase, registered object role, syscall, errno, elapsed time, deadline, and `outcome_indeterminate`. It exposes that observation through authenticated status and emits best-effort structured stderr and metrics, but writes no Runtime Audit record, failure marker, or clean release. After signal exit, the next process follows ordinary startup, derives every condition anew from exact durable bytes, and requires requalification only when those checks independently confirm Storage Capability Missing. On a claimable next session, native inspection returns predecessor, candidate, or a repair-requiring third state; predecessor may abort, candidate must finalize, and published state never rolls back. Normal shutdown strongly synchronizes a Clean Shutdown Boundary binding the current session, predecessor Audit Head Hash, and unused suffix through reservation high-water, then attempts one slot advancing to its resulting Audit Head Hash and `CLEAN_RELEASED`. If the Boundary is exact but the Anchor write fails, the next Bootstrap accepts the prior closed tail and makes only its own claim. The Daemon Instance Lock and Runtime Identity Lease prevent a second serving process for the Runtime, while Device Executor ownership remains an in-process invariant; no separate device lease or orphan Backend process exists.

Initialization Manifest Repair accepts two agreeing valid Locator slots or one sole valid degraded slot as the unique identity source. It requires the established Anchor, exact current qualification records, usable Runtime Metadata publication staging, and writable verifiable Audit; Control inspection must complete but a Control Repair or Control-schema Migration No Path finding remains independent and does not block this repair. Any identity ambiguity, unrecoverable Locator or Anchor, missing capability, session barrier failure, Metadata or Audit repair condition, or Cross-Authority Damage rejects before copying evidence.

Every Runtime Bundle includes the exact Locator-selected Initialization Manifest bytes and File Hash. Restore only verifies equality with the unchanged target Locator, while Clone retains those source bytes as lineage and creates a new destination Manifest under the new ID; no source Manifest becomes destination authority.

A broken selected qualification-record chain is eligible for explicit Qualification Lineage Reset rather than orphan adoption. Under offline authorization and the qualification lock, reset first writes and fully synchronizes one immutable content-addressed Qualification Lineage Reset Record binding filesystem UUID, Profile, exact prior slot hashes or typed invalid observations, any selectable prior Lineage ID, the new random Lineage ID, Policy Identity, and tool build. It then atomically publishes two equal `NO_PREDECESSOR` Head slots binding the reset-record File Hash, retains every prior and orphan record plus every Runtime reference, and creates no Runtime Receipt or Audit evidence.

Rebind Tool Custody is on the candidate-qualified Identity-root volume and contains only fixed-owner bounded-mode regular files named by one canonical manifest: the executable and every non-system dependency. Before every initial execution or resume, the offline tool reopens every entry without following links and verifies type, owner, mode, individual File Hashes, manifest, and token-bound bundle digest; any mismatch blocks execution. Symlinks, special files, path identity, and opportunistic rebuilds never satisfy custody.

Anchor evolution is an explicit forward maintenance operation under both locks. A supported migrator reads the highest valid old-major payload, writes and synchronizes the equivalent new-major payload into the inactive format-neutral envelope, verifies it, and only then selects it through the normal two-slot generation rule; at least one valid predecessor remains throughout. A binary writes only its current Anchor Format Major. A new payload too large for the fixed envelope has no in-place migration, counter exhaustion has no wrap or reset, and an incompatible binary must use a compatible Bundle and binary to Clone into a new Runtime rather than replace or downgrade the Anchor file.

After Bootstrap has established every non-Backend readiness prerequisite, the daemon starts the in-process Device Executor and performs Native Adapter Initialization on its owner thread. Device Executor Failure is process-wide: it fails live dependent work, invalidates every native handle, and terminates the daemon rather than restarting the owner thread in place. The next daemon performs ordinary Bootstrap with empty Residency and inference state and remains behind the Process Reclaim Barrier until exclusive lifetime locks and fresh system Resource Evidence establish the new baseline. A host service manager may apply whole-daemon relaunch backoff, but it is outside the inference architecture and is not persisted in Runtime Control State. An unresponsive Backend operation first receives the cooperative Device Control Signal; if it misses the certified next-safe-point bound, the Operation Watchdog terminates the whole daemon after a bounded diagnostic grace.
